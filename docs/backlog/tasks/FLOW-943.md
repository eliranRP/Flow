# FLOW-943 · The main screens' server reads take less time, with the same answers
- **Type:** BUG · **Status:** in-progress (perf/main-screens-load, 2026-10-21) · **Depends on:** [FLOW-804](FLOW-804.md). **Source:** Owner report 2026-10-21: the main screens (Home, Projects and a project, company profit, cash and forecast, Review) take more than a second to load.
- **Files:** `supabase/migrations/20261021120613_main_screens_speed.sql`, `supabase/migrations.lock`, `supabase/tests/database/main_screens_speed.test.sql`, `docs/decisions/0193-client-privileges.md`.
- [x] Measured read-only in production on the largest company (about 800 lines): each screen fires its reads in parallel and the app caches them for 30 minutes, so there is no client waterfall to remove. The time is in the database, and most of it in a few shared pieces that every read repeats.
- [x] `private.pnl_lines` (scanned by every P&L, cash and profit read, often several times) called three small SQL helpers per line that Postgres could not inline, because each set `search_path`, and ran two aggregates per line to find its loan and line splits. The per-line helpers (pure expressions over their arguments) no longer set a configuration, so they inline, and the split totals are grouped once and hash joined. A pass over a company's lines takes about a third of the time.
- [x] `get_breakdown` read `private.breakdown_rows` twice when grouping by category; it reads it once.
- [x] `recurring_changes` and `recurring_this_month` read `private.recurring_stream_lines` three times, `expected_months` twice. `private.recurring_parties` returns this month's amount, latest line and line count and whether the charge pays a loan, and finds each charge's last bill in one grouped pass; `recurring_arrivals` and `expected_months` read those instead of the lines.
- [x] `main_screens_speed.test.sql` pins the outputs of every rewritten read on invented books; the same assertions pass on the definitions from before the migration. On two invented companies, 266 read outputs (every Home, project, profit, cash and recurring read, several periods and days) are byte for byte the same before and after.
- [ ] Left for later: `company_next_month_inputs` reads `project_category_months` once per active project (the slowest read on the company profit page); `get_project` and `project_recurring_arrivals` still repeat work; a new PostgREST connection pays a cold start on every first read, and the Micro instance's CPU is shared.
