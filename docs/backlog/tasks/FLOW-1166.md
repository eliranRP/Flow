# FLOW-1166 · Database lifecycles: tie the columns of a state together, and close the direct writes around them
- **Type:** SMALL CYCLE · **Status:** done (#1143; parts #1131, #1134, #1136, #1138, #1140, #1141) · **Depends on:** [FLOW-1160](FLOW-1160.md)
- **Source:** the state machine read of 2026-11-10 ([map](../../tech/state-machines.md), FLOW-1160). Read in the migrations, not run. One migration per box or per table; each first counts the rows that would break the new rule and says what happens to them.
- **Files:** new migrations under `supabase/migrations/`, pgTAP under `supabase/tests/database/`, `packages/shared/src/database.types.ts`.

- [x] `loans`: any status may follow any other, and the app still writes the table directly, so a refinance link on an open loan and a two-loan cycle can be stored, and a loan can be inserted already closed without `loans_close_check` firing. Decide whether `paid_off` and `closed` differ anywhere; today no query tells them apart. (Part 1: the link and the pair; part 5: the insert check; `paid_off` and `closed` the same, decided; the move of the app's direct writes onto RPCs is [FLOW-1172](FLOW-1172.md).)
- [x] `transactions`: a void line is removed (`transactions_void_removed_chk`; a removed line need not be void), and a suggested category is never the owner's (`transactions_suggested_chk`); the other three provenance flags are independent (part 3).
- [x] `review_queue`: the open-row index is not unique, so writers delete each other's duplicates; `skipped` means the owner's skip, a SUMIT company switch or a transfer match, with nothing stored to tell them apart. (`reason` and `resolved_at` are tied by CHECKs in part 3.)
- [x] `projects`: `finished_on` is not tied to `status`, and a finished project still takes filings from `reassign_transaction` and `resolve_review`. (Part 1: `projects_finished_chk`; the filings stay, decided 2026-11-13.)
- [x] `company_integrations`: `enabled` and `mode` can disagree (`enabled` with `off`). (Part 5.)
- [x] `prepaid_schedules`: an `active` row with an end date can be stored; a schedule whose payment line was removed stays `active` and posts nothing. `books_closed_through` is read by five functions only: say what the closed date is meant to lock. (Part 1: `prepaid_schedules_ended_chk`; part 2: the lock; part 5: the end on a removed payment.)
- [x] `company_invites`: an expired invite is never stored as such, so it blocks a new invite to the same address until the owner cancels it; `reopen_invite` does not check the expiry.
- [x] `reassign_undo`: the undo restores its snapshot without checking that the line still reads as written, so an older undo overwrites later edits.
- [x] `jev_usage`: a run that never finishes holds its reservation until the day rolls; `jev_line_failures` are never cleared by a later success. (Part 5.)

**Acceptance:** pgTAP that each new `CHECK` refuses the meaningless row and each move refuses the wrong starting state; the cross-company sweep stays green.

**Decided by the owner, 2026-11-10:** `paid_off` and `closed` loans behave the same; both stay as labels and no rule is added between them (approved option "Same behaviour"). The books-closed date locks everything in a closed month: the owner's edits (filing, splits, manual bookings, deletes) are refused, and a sync no longer changes a line dated in it (approved option "Everything"). A late bank correction to a closed month therefore does not come in until the date is moved back.

**Decided by the owner, 2026-11-11:** when a sync brings a change to a line dated in a closed month, the stored line stays as it is, the change is kept aside and the line is flagged for review, so the owner can reopen the month and take it or leave it (approved option "Hold it and tell me"). The task is split: first the rules that only tie columns together and cannot refuse anything valid today (loans, projects, tagging settings, prepaid, invites); then the closed-month lock and the review-queue changes as their own PRs, each planned with the owner first (approved option "Safest first, then ask").

**In #1131 (part 1):** `loans_refinance_chk` and the trigger `loans_refinance_pair`, with `mcp_undo` and `private.loan_restore` patched to keep them; `projects_finished_chk`; `prepaid_schedules_ended_chk` (replacing `prepaid_schedules_ended`); `company_invites_decided_chk`; `invite_member` cancels an expired pending invite and makes the new one. Each CHECK is `NOT VALID` (it guards new writes); the count of breaking rows in production was 0 for every one on 2026-11-11, so each can be validated. **Left:** `company_integrations` (no rule holds for every writer today: the settings card keeps a remembered mode with `enabled` off, and the MCP setter stores `enabled` with mode `off`; the setter must normalise first); `reopen_invite` and the expiry (refuse or extend: a product choice); the closed-month lock; the review queue; the ledger line's columns; the undo ticket; Jev usage.

**Decided by the owner, 2026-11-11, for the closed-month lock (part 2):** a sync change held in a closed month shows in the existing review queue, with its own reason; no new screen; to take the change the owner moves the closed date back and the next sync applies it (approved option "In the review queue"). An edit the owner tries in a closed month (file, split, book by hand, delete) is refused with a message that says the month is closed and where to reopen it, with no reopen button (approved option "Refuse with a clear message"). The new sentences go to the owner before they ship.

**The closed-month lock, as planned and decided with the owner on 2026-11-11:**
- The lock is on the exact date: a line is closed when its `doc_date`, or a non-null `cash_date`, is on or before `books_closed_through`, and the line is in a report (posted, not removed). A pending line is free until it posts. A write that changes only `cash_date` is tested on the old and new `cash_date` alone, so a closed month's invoice can still be marked paid in an open month.
- A person's edit that would change a report column of a closed line is refused by row triggers on `transactions`, `allocations` and `overhead`, plus a check in `set_line_parts` and `set_loan_parts`; every owner RPC, MCP tool and undo is covered without being patched. The message is the existing `the books are closed through YYYY-MM-DD`.
- A sync change to a closed line is held in a private table and shown in the review queue with the reason `closed_month_change`; the stored line stays as it is. The next sync after the owner moves the closed date back applies the held change itself. אישור on the card leaves the line as it is and closes the card; a later reopen still brings the provider's change in.
- A filing the sync re-derives for a closed line (a supplier rule, a SUMIT section) keeps the stored value, with no hold.
- A brand-new bank line dated in a closed month enters as any other (approved option "Let it in").
- A category delete, merge or move that touches a closed line is refused whole (approved option "Refuse the whole action").
- Settings that move a closed month's figures without touching a line (the cash basis, a category's P&L or cash flag, account binding, the overhead project) are not locked here; a follow-up task (approved option "Not now, file a follow-up").
- The wording, approved as written: the refusal toast "הספרים סגורים עד {date}. כדי לשנות שורה מהתקופה הזו, הזיזו אחורה את תאריך הסגירה דרך עוזר ה־AI."; the card's reason "שינוי מהבנק ממתין: התקופה סגורה בספרים." (and "שינוי מ־SUMIT ממתין: התקופה סגורה בספרים."); its details "סכום חדש: {amount}", "תאריך חדש: {date}", "הבנק ביטל את השורה.", "המסמך נמחק ב־SUMIT.", "השורה עברה לסופית."; its hint "כדי לקבל את השינוי, הזיזו אחורה את תאריך הסגירה. הרענון הבא יכניס אותו."; after אישור "השורה נשארת כמו שהיא.".
- In three PRs: (a) the app's refusal message and the triggers for a person's edits; (b) the held sync changes, the review reason and `leave_held_change`; (c) the review card and the MCP tool.

**In #1134 (part 2a):** `private.books_closed_hit` is the one definition of a write that touches a closed period; row triggers on `transactions`, `allocations` and `overhead` refuse it when a person writes, and `set_line_parts`, `set_loan_parts` and `set_loan_parts_review` check the line the same way. `follow_invoice` leaves a closed receipt's filing when a person files its open invoice. A bulk action that reaches a closed line is refused whole, a project or loan delete included. The app says so with the approved sentence (`booksClosedNote`), with no retry. With no closed date set (every company on 2026-11-11) nothing is refused. **Left:** a sync still changes a closed line (part 2b); an open review item on a closed line cannot be approved until the period is reopened, so close the books after the review queue for that period is empty (whether the setter should refuse a close with open items is a question for the owner).

**Decided by the owner, 2026-11-12:** `set_books_closed_through` refuses a close while lines dated on or before the date are still open in the review queue, as it does for unposted prepaid rows (approved option "Refuse the close"). The company's settings show one read-only line with the closed date; setting it stays with the AI assistant (approved option "Show it, read-only"). The held-changes step goes ahead next (approved option "Yes, continue").

**In #1136 (part 2b):** a sync's change to a provider fact of a closed line (amounts, VAT, dates, status, currency, direction, a void, a removal) is held in `private.closed_line_holds`, and the line, its allocations and its overhead stay as they are; filing the sync re-derives (category, project, role, supplier, customer) is kept silently; a new line dated closed enters. The next `upsert_connector_lines` replays a held change once its line is no longer closed, before the fetched lines. Each hold has one open review row with the reason `closed_month_change`, and `list_review` carries `held`; `leave_held_change` / `mcp_leave_held_change` (undo kind `held_change_left`) leave the line as it is and approve the row. `follow_invoice` keeps a closed receipt's filing for every writer, and `jev_prefill` skips a line with a hold. `set_books_closed_through` refuses a close while a line the date would close is open for review (`approve the open review lines first`). **Left:** the closed-month triggers still refuse a person only (the Jev job, `save_split`, `set_supplier_settings`, `map_budget_section`, `replace_sumit_connection`, the cascades and the prepaid cron run as the service role and were not all traced, so widening could make a job raise); `fill_suggested_category` can fill a closed line whose stored category is null; a hold on a pending line is left out of the waiting counts; the review card, the MCP tool and the read-only closed-date line in settings (part 2c).

**In #1138 (part 2c):** the review card for `closed_month_change` (the approved wording; the reason by provider, the detail lines that apply, the hint; אישור alone, through the queue's approve, calls `leave_held_change` and says "השורה נשארת כמו שהיא."; no pickers, שינוי or דלג; a viewer reads it), the MCP write `leave_held_change` (undo `held_change_left`) with `list_review`'s spec and the guide describing `held`, and the read-only "הספרים סגורים עד" row on העסק. No migration. **Left:** the app's אישור has no ביטול on this card (the assistant's undo can reopen it); the review queue's approving flag is still a ref, not a table.

**In part 3:** one migration, rules only, each kept by every writer today (production counted 0 breaking rows on 2026-11-13). Part 1's four CHECKs are validated. `transactions_void_removed_chk`: a void line is removed; only this direction, since the SUMIT sweep and `replace_sumit_connection` remove a line without voiding it and a swept document sent again comes back. `transactions_suggested_chk`: `category_suggested` never with `user_assigned` or `category_assigned` (the trigger `fill_suggested_category` already cleared it on every write); `user_assigned`, `project_assigned` and `category_assigned` are written independently, so no rule ties them. `review_queue_resolved_chk`: open ⇔ no `resolved_at`. `review_queue_reason_chk`: the six reasons the code writes, or none; it is the one list (the app and flow-mcp compare single reasons only). `sync_review_queue` drops its code for the retired `pending_income` reason, and the test fixtures that stored a void line without its removal, a closed row without its time or a made-up reason now store what a writer would. The checks are validated in the same transaction (the tables are small; ACCESS EXCLUSIVE for milliseconds). **Left:** the unique open-row index and what `skipped` means (next, with the owner); `reassign_undo`; `jev_usage`; `company_integrations`; `reopen_invite`.

**Decided by the owner, 2026-11-13, for part 4:** a late undo of a filing is refused when the line was changed since, with a short message, and the newer edit stays (approved option "Refuse it"). The review queue holds one open row per line; an undo that would reopen an old row while a newer row for that line is open succeeds, the old row stays closed and the newer one is the card shown (approved option "Keep the newer card"). The refusal sentence goes to the owner before it ships.

**In part 4:** one migration (`20261113060409_review_row_undo_rules.sql`), as decided on 2026-11-13. **One open review row per line:** `review_queue_open_line_key` is unique on the line among open rows and replaces `review_queue_open_idx` (the reads by company use `review_queue_company_idx`); production had no line with two open rows. The two paths that could make a second one, `reopen_review` (a skip and an approval alike) and `undo_reassign`, now reopen only when no other row of the line is open; otherwise the undo still succeeds, the newer row is the card, a skip stays skipped, and an approved or changed row whose filing came back is deleted (an invoice's paired receipts go back first, as on a reopen; kept, the sync would read it as settled and never queue the unfiled invoice again). An open `split_mismatch` row still gives way to a row that comes back (`private.review_may_reopen`, which replaces the trigger's branch). Every guarded insert of an open row (`sync_review_queue`, `forecast_line_sync`, `line_split_review_sync`, `delete_category`, `undo_held_change_left`, and `set_transaction_category`'s two) is `ON CONFLICT DO NOTHING`, so a sync never fails on the index. **What closed a skip:** `review_queue.skipped_by` is `person` (`resolve_review`), `transfer` (`transfer_mark_line`) or `sumit_switch` (`replace_sumit_connection`), null otherwise and for older skips; the transfer match's undo reopens only a transfer's skip (or an unknown one), not a person's later skip. The sync's "do not queue again" already keys on the document fingerprint, which the SUMIT switch does not set, so it is unchanged. **A late undo:** `reassign_undo.written_line` keeps the line as the filing left it (project, category, role, the three flags the undo restores, allocations, overhead, and the split by category and loan payment parts the undo would leave; filled by a trigger after the filing's last write, so a paired receipt's follow is part of it), and `undo_reassign` refuses with `line changed since` under the line's lock when the line reads otherwise, restoring nothing. A sync's update of other columns does not block it; a sync's new amount does (it moves the allocation). Older tickets keep the old behaviour. flow-mcp answers it as `conflict` / `line changed since`; a loan attach's undo then leaves the line's project. The app's ביטול says "השורה שונתה מאז. הביטול לא בוצע." with no retry (the wording waits for the owner's confirmation before the merge). **`reopen_invite`** refuses an invite past its expiry. **Left:** `loans`, `projects` (the finished project's filings), `company_integrations`, `prepaid_schedules` and `jev_usage` as listed above; a reopen racing a sync's insert for the same line can fail once with a unique violation (a person's undo; a retry succeeds).

**Approved by the owner, 2026-11-13:** the refusal toast reads "השורה שונתה מאז. הביטול לא בוצע." (approved option "Shorter").

**Decided by the owner, 2026-11-13, for part 5:** a finished project keeps accepting filings, since late invoices and corrections belong in its profit; no rule is added (approved option "Keep accepting"). A prepaid schedule whose payment line is removed is ended at that point, its posted months stay, and it is listed as ended because its payment was removed, so the list and the AI assistant show why (approved option "End it and tell me").

**In part 5 (the last):** one migration (`20261113160900_lifecycle_last_rules.sql`), as decided on 2026-11-13. **Prepaid:** a schedule whose payment line is removed (a bank void, the SUMIT sweep, a SUMIT company switch, or a held void or removal once its month is open and the next sync applies it) is ended in the sync's own statement by the trigger `transactions_prepaid_removed`: its planned months are dropped, the posted months stay, nothing is written to the ledger (`end_mode` `keep`), and `prepaid_schedules.ended_by` is `payment_removed`; the owner's or the assistant's `end_prepaid_schedule` writes `person`; null on schedules that are not ended and on those ended before (`prepaid_schedules_ended_by_chk`). The automatic end (`private.prepaid_end_removed`) takes its locks with SKIP LOCKED and does only deletes of planned rows and one update, so it never makes a sync raise; when a prepaid write or the daily job holds the schedule, the daily job ends it on its next run (`prepaid_end_removed_all`, which also ended the schedules already in that state when the migration ran). A line that comes back leaves the schedule ended; the owner deletes it and makes a new one. A prepaid undo restores `ended_by` and ends a schedule it puts back on a removed line with planned rows (active, or ended with its months planned again by the undo of a delete); an ended schedule on a removed line keeps no planned row, so none is left for the books-closed check to count as due. `list_prepaid_schedules` and `get_prepaid_schedule` return `ended_by`. The app shows no prepaid schedule, so no screen changed. **Loans:** `loans_close_check` fires on an insert too (a new loan has no payment, so it passes; `restore_loan` of a closed loan included). The app's direct writes stay, each covered by the table's checks and triggers; their move onto RPCs is [FLOW-1172](FLOW-1172.md). **Tagging settings:** `company_integrations_on_chk` (enabled only with mode shadow or auto), since every reader treats Jev as on only when both say so; `set_company_integration` (the card and `set_jev_mode`) stores enabled false with mode off, the jev_mode undo puts back and compares older tickets the same way, and the stored rows with enabled and mode off were set to enabled false (no reader tells the two apart). **Jev usage:** a reservation with no finish counts for 15 minutes after it was made (an Edge run lives at most 150 seconds, 400 on a paid plan), so a live run keeps its reservation and a dead one stops holding the day's cap; a late finish still records its calls. `jev_finish_usage` deletes the failure rows of the company's lines that now have a suggestion; a line that keeps failing keeps them and its backoff. **Left:** nothing in this task; the app's direct loan writes are FLOW-1172, and the tagging failure that can never pass (it still retries daily) stays in [FLOW-1168](FLOW-1168.md).

**Decided by the owner, 2026-11-13:** the months a prepaid schedule already posted stay in the books when its payment is removed, until the owner or the AI assistant deletes the schedule; nothing is reversed automatically, and the tool's description says so (approved option "Keep, and say so").
