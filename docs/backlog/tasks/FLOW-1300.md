# FLOW-1300 · Perf: every API read stalls up to 8 s in production at times (the recurring reads average 0.64 to 0.91 s against 0.1 to 0.14 s warm)
- **Type:** MEDIUM (perf, investigate first; priority) · **Status:** ready · **Source:** the 2026-11-24 daily report's diff review (indexes, pre-existing): production `pg_stat_statements` since 2026-11-21.
- **Files:** to be found; start at `private.recurring_parties`, `public.recurring_schedule`, `public.missing_bills`, `public.expected_months` and their callers.

Since the 2026-11-21 reset, production's `pg_stat_statements` shows `recurring_schedule` at 392 calls, mean 643 ms, max 7,970 ms; `missing_bills` 339 calls, mean 653 ms, max 7,832 ms; `expected_months` similar. Warm, as Flow QA in a read-only transaction, they take 90 to 140 ms. The index reviewer found no missing index (every inner read is an index scan on a small table), so the gap is first-call cost, concurrent calls, or a few slow companies. A phone that meets a 0.6 to 8 s answer misses 0.5 s by far.

- [ ] Split the stats: by company size, first call in a connection versus later, and calls that overlap (Home sends several of these at once). Use the read-only pattern of the daily report; never write.
- [ ] Report what the time is, with the numbers, and propose the fix (for example one shared `recurring_parties` per request, a cached plan, or fewer concurrent calls) as a plan in the PR before building.

**Update 2026-11-26** ([the daily report](../../qa/perf/2026-11-26.md), section 5): the gap is not specific to the recurring reads. Since the 11-21 reset, 28 distinct API read statements have a max over 5 s, most at 7.4 to 8.0 s; a trivial read (`count_utility_refunds`, 575 buffer hits, min 28 ms) averages 571 ms with a 7.8 s max. No disk reads (`shared_blks_read` about 0), JIT off, no deadlocks, and the top total time is all the app's own `authenticated` calls (no sync job): the time is waiting inside the database, most likely memory pressure when several calls run at once on a small instance (see the 11-27 update). It is getting worse: calls since 11-24 average about 856 ms for `recurring_schedule` and 912 ms for `missing_bills`. `company_forecast` has the highest mean (1.5 s over 65 calls, min 209 ms). The 11-25 and 11-26 sweeps met these stalls (reads of 3 to 5.9 s; the project page did not show its data in 6 s in any of 3 runs on 11-26).

- [ ] Split the stats by time of day (the daily sweep and `pnpm latency` run at about 01:15 to 01:50 UTC) and by how many calls overlap; read the Supabase dashboard's CPU graph for the same windows (the owner can, the steward's token cannot).
- [ ] Decide between fewer concurrent calls per screen (cold Home sends 23 requests in 4 waves) and a larger compute size (the owner's call: it costs money).

**Update 2026-11-27** ([the daily report](../../qa/perf/2026-11-27.md), section 5): not CPU. The owner's dashboard shows CPU at 3 to 12% while RAM is full, swap is about RAM-sized and memory commitment is flagged severe on the 0.5 GB instance. The index reviewer measured a Postgres backend growing from 1.6 to 24.6 MB after 8 distinct reads (cached plans, SQL function contexts, catalog cache); PostgREST recycles its 7 pool connections within minutes, so memory is per burst, not per day. Reads with a 1 ms floor stall to 6 s with no disk reads, so the stalls look like whole-process freezes under memory pressure. The statistics undercount them: `statement_timeout` is 8 s and killed calls are not recorded (19 reads have a max of 7.16 to 7.97 s). A first call costs no more than later ones. Next, with the owner's go (11-27): FLOW-1343 (Home stops loading setup for a card that draws nothing, 7 fewer requests for an owner mid-setup who has resumed) and FLOW-1344 (at most 4 reads in flight), then measure. Free dashboard options for the owner, not taken for now: a restart, a smaller Data API pool, a smaller `shared_buffers`.

No new maximum (still `recurring_schedule`'s 7,970 ms). One day is not proof. The next reports compare the same before-and-after sums.
