# FLOW-1311 · Perf: category months kept current on write (only if the forecast read needs it)
- **Type:** LARGE (perf) · **Status:** blocked (FLOW-1307) · **Source:** the FLOW-1275 [plan](../../tech/flow-1275-server-side-math.md), slice 12 (owner approval 2026-11-24).
- **Files:** a migration (`public.category_month_sums`, its RLS, `private.category_month_sums_rebuild`, deferred statement-level triggers, `private.project_category_months_lean` reading it); pgTAP parity per write path and a dependency test; a line in CONTRIBUTING's migration rules.

Built only if FLOW-1307's measured read is over its 300 ms budget; otherwise closed unbuilt. Today `private.project_category_months_lean` takes 60 ms for Flow QA's 14 projects on every inputs call; one project's recompute is 24 ms warm, 47 ms cold (read-only, as Flow QA).

- [ ] The table holds every month by company, project, category and currency; the read picks the window from `p_today` (no midnight job).
- [ ] The trigger tables and columns are derived, not listed by hand: what `private.pnl_lines` depends on (`pg_depend`, columns from `refobjsubid`) and what `project_category_months_lean` reads, with every view resolved recursively to its base tables. `private.pnl_lines`, `private.split_parts` and `private.loan_parts` are views (the last two over `legs`), so they get no trigger; today the base tables are `accounts`, `allocations`, `categories`, `companies`, `legs`, `transactions` and `review_queue`. A pgTAP test computes them and fails on a base table with no sums trigger, or a referenced column missing from its trigger's `update of` list.
- [ ] The write paths of the plan's section 3, among them `legs` insert, update and delete (`journal_entry_update` moves legs between transactions), collecting keys for the line's project, a split part's own project and, for a shared line, every project in its `allocations`, on both the old and the new side of an update; `review_queue` inserts and deletes as well as status changes; `transactions` on every column that changes a sum (`removed_at`, `line_status`, `pnl_role`, `direction` and `currency` included; not `category_id`, which comes from the leg), with the same keys as `legs` on both sides, so a `pnl_role` change between project and shared reaches the old and the new projects (production has about 74 transaction updates an hour, mostly sync); `companies.overhead_project_id`; `categories.kind`. A deferred constraint trigger rebuilds the collected keys once per transaction.
- [ ] A migration or backfill that disables triggers (`alter table ... disable trigger`, `session_replication_role = replica`) must end by calling `private.category_month_sums_rebuild` for the companies it touched; CONTRIBUTING says so, and the daily report's read-only parity check catches one that does not.
- [ ] pgTAP: after each kind of write, the table equals the aggregate for every fixture project; the cases include a line removed, a line posted and a `pnl_role` change between project and shared, each on a project line and on a shared line with two allocated projects, a leg of a shared line changed, a split part's project changed and the overhead project changed.

**Acceptance:** the inputs and forecast reads answer exactly as before and faster (measured as Flow QA, read-only); the write paths' added time measured on a local database (a 200-line sync, a split, a review answer, a category switch).
