# FLOW-1190 · Plan: cache recurring_parties per company
- **Type:** PLAN FIRST (perf) · **Status:** plan-first · **Source:** the owner's answer of 2026-11-13 to "Recurring charges are recomputed from scratch by about 10 reads (~80–95 ms each, several per screen). Caching the result per company would save ~80 ms on each read after the first, but a cache can show a stale charge briefly after a write.": "Plan it first: I write a plan for a per-company cache (what invalidates it, how stale it can get) and bring it to you before building."
- **Files:** to be named by the plan; likely a new migration in `supabase/migrations/` (a cache table and the function change), `supabase/migrations/` writers that must invalidate it, and `supabase/tests/database/` for pgTAP.

`private.recurring_parties(company, today, overrides)` is the recurring schedule's one computation. Grep of the latest migration bodies (2026-11-13) finds these callers of it: `public.expected_months` (reads `pays_loan`), `public.company_next_month_inputs`, `private.recurring_arrivals_json`, `private.project_recurring_arrivals`, and, in `20261113141912_recurring_setwise.sql`, `private.recurring_handovers` and `private.recurring_match_suggestions`. The plan confirms the rest of the named reads (`recurring_schedule`, `missing_bills`, `recurring_changes`, `payment_recurring`, `party_charges`, `get_setup_suggestions`) before anything is built.

The plan, for the owner before any build:
- The list of reads that call the function, from the latest bodies, and which of them a cache would serve.
- A cache table keyed by company and day (`today` is an argument, so a day changes the key), with the overrides flag in the key.
- Which writes invalidate it: transactions, transaction legs, `recurring_overrides`, `recurring_matches`, and every other table the function reads (listed from its body, not from memory). A trigger or an explicit call from each writer.
- How stale a read can be: the longest a charge can show before the write's own refresh, in the cases a write comes from another session or from the bank's sync, and what the screen shows meanwhile.
- The expected saving per read after the first, and a measurement: the same screens on production, as the daily perf report measures them, before and after, with `EXPLAIN` for the function.
- What a failed cache write does (the read falls back to the computation), and the rollback.

**Acceptance:** a plan the owner approves before any build. The plan is written in this task and names the owner's approval; no migration, cache table or function change is merged before that.
