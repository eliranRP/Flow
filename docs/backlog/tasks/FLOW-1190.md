### 3. The cache's shape

- Table `private.recurring_parties_cache`: `company_id uuid`, `today date`, `version bigint`, `rows jsonb` (the 20 columns, one array), `computed_at timestamptz`. Primary key `(company_id, today, version)`. Foreign key to `companies` with `on delete cascade`.
- Key: company, today, overrides flag. Only `overrides = true` is cached, so the flag is implied and not stored. `version` is explained in 5 and is what makes the cache safe.
- Value: one jsonb array per key. One row means one atomic insert, so a reader never sees half a set. The wrapper returns it with `jsonb_populate_recordset` over the function's own return type, so the columns match the computation.
- A second small table, `private.recurring_cache_version (company_id primary key, version bigint)`, holds each company's current version.
- Where it lives: schema `private`. RLS on, no policies. `revoke all` from `public, anon, authenticated, service_role`. Only the `security definer` wrapper and the trigger function (`set search_path = ''`) touch it. No view, no grant.
- Size: one row per company per day, holding one entry per recurring charge. Not measured. Step 1 of a build is to count what `recurring_parties` returns for the largest company on production (read-only) and size from that. Old days are purged (4).

### 4. Invalidation

One trigger function, `private.recurring_cache_bump()`, used by statement-level triggers with transition tables. For each table in 2 there are three triggers (insert, update, delete), because PostgreSQL does not allow one transition-table trigger on several events, nor a column list with a transition table. That is 15 triggers and one function. Each reads `select distinct company_id` from its transition table, bumps `recurring_cache_version` for those companies and deletes their cache rows of earlier versions. All in the writer's own transaction.

| Table | Writers (examples, all covered by the trigger) |
| --- | --- |
| `transactions` | manual entry, review, split save, remove and undo, loan matching, the daily prepaid and recurring jobs, bank sync (`upsert_connector_lines`, called by `mercury-sync`), invoice sync (`upsert_sumit_documents`, `sumit-sync`) |
| `legs` | `private.post_lines` on every transaction write, split and loan part saves |
| `categories` | category edits (only `excluded_from_pnl` matters, but a transition-table trigger cannot say so) |
| `recurring_matches` | `mcp_answer_recurring_match` |
| `recurring_overrides` | `write_recurring_override`, `set_payment_*`, `mcp_set_line_*` |

- Bulk writers (bank sync, imports, `post_lines`) run one statement over many rows. A statement trigger fires once per statement, not per row. The cost is the transition table (rows copied to a tuplestore). To be measured on Flow QA before the build is approved.
- Service-role writers (the edge functions use `admin.rpc`) fire the same triggers. A trigger does not look at the role.
- Outside the triggers: `TRUNCATE` (none found in the migrations, functions or scripts for these tables) and `session_replication_role = replica` (found only in three pgTAP test files: `loan_kinds_rates`, `push_new_and_weekly`, `push_notifications`). Also a **migration that changes a function body** listed in 2 leaves old rows stale. Each such migration must end with `truncate private.recurring_parties_cache`. This becomes a review checklist line.
- `today` changing daily needs no invalidation: the day is in the key. Old days are purged when a company fills a new day (delete its rows with `today < flow_today() - 1`), and by one daily statement as a backstop.
- Cascading deletes (a company, a project) are tested in pgTAP to confirm the statement trigger fires.

### 5. Staleness

Precisely:

- **A read after a committed write never sees stale data, provided each cache row is stamped with the version it was computed under.** The trigger bumps the version in the writer's transaction, so it commits with the data. A reader reads the version and computes in one snapshot and stores the rows under that version. A read after the commit asks for the new version, finds nothing and computes.
- **Without the version, a delete-only design has a hole.** A reader that took its snapshot before the commit computes old data. The writer commits and deletes (finding no row). Then the reader inserts the old rows, and they stay until the next write. This is why the plan uses a version. A read already running when the write commits may still show old data, as every read does today under read committed.
- The writer's own transaction sees its own bump, so a read after a write in the same transaction recomputes.
- Paths that write outside triggers: none found, other than the three in 4 (a function-body migration, `TRUNCATE`, replica mode). All three are controlled.
- What the screen shows meanwhile: the last committed state, as today. There is no window in which a charge shows that a committed write has removed. The cache adds no delay.

### 6. Expected saving and how it is measured

- Saving: the ~80 to 95 ms the task cites, on every call after the first one of the day or after a write, for each of the ten read callers. Several calls on one screen share one fill. No other figure is claimed.
- A call that misses pays the same compute plus one insert.
- Before and after, `EXPLAIN (ANALYZE, BUFFERS)` as the Flow QA user (the sandbox company, see `docs/runbooks/qa-user.md`) in a read-only transaction: `private.recurring_parties`, then `recurring_schedule`, `expected_months`, `company_next_month_inputs`. A read-only transaction cannot write the cache, so the "after" run needs one normal call first, in a separate transaction, to fill it. This is also a risk in 8.
- Then the daily perf report (`docs/qa/perf/`): the Recurring (`recurring_schedule`), Forecast (`expected_months`) and Company profit (`company_next_month_inputs`) rows, p50 and the screen-ready numbers, for the days before and after the deploy.
- Also measure the write side on Flow QA, before and after: a bank-sync style bulk upsert and a single line edit, to price the triggers.

### 7. Failure and rollback

- The wrapper does the cache read and write inside a `begin ... exception when others then` block. If the read or the insert fails (read-only transaction, lock timeout, any error), it computes with `recurring_parties_compute` and returns that. The answer never depends on the cache working.
- A trigger failure would fail the writer's statement. The triggers do one update and one delete by primary key and are kept minimal. Decision for the owner: should a trigger swallow its own error (the version could then be missed, so stale) or fail the write (safe, loud). The plan chooses fail the write.
- Rollback: one migration. Drop the 15 triggers and the trigger function, restore `recurring_parties` to the compute body (rename back), drop the two cache tables. Nothing else changes, since the callers are untouched. It uses the repo's `lock_timeout`.

### 8. Risks

- **Concurrency.** Two readers filling the same key: `insert … on conflict do nothing`, and the loser returns its own computed rows. Readers at different versions write different keys. The version covers the race in 5.
- **The version row is a hot row.** Every write transaction to a company holds a lock on it until it commits, so a long bulk sync (one transaction) would block other writers of that company. If the build measurement shows this, the options are a deferred constraint trigger (bump at commit) or delete-only with the race closed another way. Owner decides after the measurement.
- **Trigger cost on hot write paths.** `transactions` already carries many row triggers from earlier migrations, and every transaction write also rewrites `legs` through `post_lines`, so one user action fires the bump twice. Transition tables take no column list, so a write to a field the function does not read (a note, a file) still invalidates. The plan accepts this and measures it (6).
- **Read-only transactions cannot fill the cache.** A read run read-only computes every time. A PostgREST GET of a stable function may run this way too (to verify before the build; the app mostly calls with POST). The wrapper cannot be `stable`; it must be `volatile`, which the planner treats differently from today's `stable` SQL function (no inlining into the caller's query). To check in `EXPLAIN` on the first callers.
- **Day cardinality.** Only today is cached (1). Other days compute.
- **Correctness parity.** A pgTAP file in `supabase/tests/database/`: for a seeded company and every day-shape the callers use, the cached rows equal `recurring_parties_compute` for the same inputs (`except` both ways, all 20 columns). Then a sequence of writes to each of the five tables (insert, update, delete, a cascade, a bulk statement, a rolled-back writer) with a cached read after each, equal to the computation. One test for a failed cache insert (the fallback) and one running the wrapper in a read-only transaction. The existing `recurring_*.test.sql` files must pass unchanged.
- **Empty companies.** A company with no recurring charge still caches one empty row per day. Small.
