# FLOW-1278 · Perf: Profit's repeat visit does not fall back to skeletons while kept figures refresh
- **Type:** SMALL (perf) · **Status:** in-progress (#PR) · **Source:** decision [0271](../../decisions/0271-half-second-by-kept-data-and-one-wave.md), item 1: kept data is drawn at once; the perf steward's trace of a repeat visit to Profit on `c48f453`.
- **Files:** `app/src/kept-rules.ts`, `app/src/kept-reads.test.ts`, `app/src/screens/company-profit-kept.test.tsx`.

A trace of a repeat visit to the month by project on production (`c48f453`, phone profile) showed skeleton bars at 750 ms, none at 1,000 ms and skeleton bars again at 1,250 ms, though FLOW-1267 keeps Profit's dashboard, breakdown and profit-months reads and puts them back before the screen opens. The page's `model` waits for the overhead project (the `companies` row, `useOverheadProject`; company-profit-screen.tsx:125, use-company-profit.ts:447), and that read was not kept: the page drew its whole loading skeleton while the kept figures sat in the cache until `companies` came back. The second skeleton is the next-month card, whose reads are not kept (see FLOW-1291).

- [x] Find why: the overhead read (`["company-overhead", "off"]`) had no kept rule, so the first frame of a repeat visit was the page skeleton. No component shows a skeleton on `isFetching`, and the kept reads' keys match the live ones (the dashboards, breakdowns and months use `keepPreviousData` and the same key).
- [x] Keep the overhead project: a rule in `kept-rules.ts`, valid only as an object with a string `id` and `name` (an unset project, `null`, is never kept, so a company with none waits for its read as before).
- [x] Tests: a repeat visit (the first visit's reads kept, a new cache restored from them, every read held in flight) draws the figures and rows and shows no skeleton; the rule's shape check.
- [ ] The next-month card still shows its loading state on a repeat visit: FLOW-1291.

**Acceptance:** a repeat visit to Profit draws the kept figures at the first frame, with no skeleton before them; the figures do not change once fresh data lands.

**Measured** (local production build against the stub backend, CPU 4×, 85 ms, 9/1.5 Mbps, 412×915, a server floor of 150 ms per read; Profit's month by project from Home, 7 paired runs, medians): a repeat visit (the app reopened in the same context, kept reads on the device) shows the figures and rows with no skeleton in the page at 456 ms against 751 ms on `c48f453` (433 to 558 against 693 to 896), and settles at 991 ms against 1,328. The first visit is unchanged (868 ms against 783: the same code, noise). The card's skeleton after the figures is still there on both (FLOW-1291).
