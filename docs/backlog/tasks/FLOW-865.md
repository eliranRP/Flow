# FLOW-865 · Every undo of a recurring switch puts back the end date it cleared
- **Type:** BUG (low; the rest of FLOW-859) · **Status:** in-progress · **Source:** the weekly security scan, 2026-11-28 (FLOW-859 review follow-ups); the owner's choice the same day.
- **Files:** `supabase/migrations/20261128164027_flow_865_recurring_undo_end_date_rest.sql` (adds `recurring_overrides.ends_on_set_at` and `recurring_handovers.to_ends_on_prior`; patches `private.write_recurring_override`, the `line_recurring` branch of `public.mcp_undo` and `public.answer_recurring_handover` in place), `packages/shared/src/database.types.ts`, `app/src/pace-write.ts`, `app/src/screens/transaction-recurring.tsx`, `app/src/screens/recurring-charge-screen.tsx`, `app/src/pace-write.test.ts`, `app/src/screens/transaction-recurring-live.test.tsx`, `supabase/tests/database/flow_1266_recurring_end_date.test.sql`, `supabase/tests/database/flow_1037_recurring_handover.test.sql`, `docs/mcp/TOOLS.md` (set_line_end_date, answer_recurring_handover), a changelog fragment.

Marking a charge recurring clears an end date that has passed (FLOW-1266). FLOW-859 made the MCP undo of a line's switch put it back. Three gaps were left:

- [x] **The app's ביטול.** The transaction page and the charge page undid a mark-recurring with `set_payment_recurring(false)` alone, so the end date stayed cleared. `runPaceChange` now returns the end date its switch cleared (`prior_ends_on`); the pick's ביטול carries it and, after the switch, writes it back with `set_payment_end`, which the app already calls. A ביטול that marks the charge recurring again puts back at once the end date its own switch clears. No new function, parameter or grant.
- [x] **The MCP undo kept a later choice only when it was a date.** It put the date back whenever the charge had no end date, even when the owner had cleared it after the write. `recurring_overrides.ends_on_set_at` now says when the end date was last written or cleared (only `ends_on` writes stamp it; the row's `set_at` moves with a pace or an amount too, and `private.mcp_writes` misses the app's writes). The undo leaves the date when the charge has an end date now or `ends_on_set_at` is after the write. The check runs before the switch goes back, which can remove the row.
- [x] **The handover's undo.** A yes (`answer_recurring_handover`) marks the new payee's charge recurring, which can clear a passed end date; taking it back (the MCP undo calls it) restored only the switches and the pace. The answer row keeps the cleared date (`to_ends_on_prior`, a repeated yes keeps the first one's), and taking the yes back puts it back under the same rule, against the answer's `set_at`. Putting back the old charge's own "recurring" keeps the old charge's end date.

A later end-date write that was itself undone still counts as the owner's word (its undo writes the date too): the date stays cleared, as it did before FLOW-859.

**Acceptance:** the app's ביטול of a mark-recurring calls `set_payment_end` with the cleared date; an end date the owner clears after the write stays cleared after the MCP undo; a handover yes taken back puts back the end date it cleared; the FLOW-1266 and FLOW-1037 pgTAP files and the new vitest cases pass.
