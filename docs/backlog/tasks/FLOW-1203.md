# FLOW-1203 · Perf: `get_property_returns` reads the property's lines once
- **Type:** MEDIUM (perf) · **Status:** done (#1184) · **Source:** the perf steward's daily diff review, 2026-11-15 ([report](../../qa/perf/2026-11-15.md)).
- **Files:** a new migration (`private.property_line`, `private.property_lines_in`, `private.refinance_transactions_in`, patching `get_property_returns`), `supabase/tests/database/property_returns_one_read.test.sql`.

`private.property_lines` reads every line of the company and filters to the property (the project comes from a CASE over the item legs, which no index serves): 23 to 60 ms a call on production. `get_property_returns` called it about 8 times, two more per purchase loan (#1180) and once more through `private.refinance_transactions` (#1181).

- [x] `get_property_returns` reads the lines once into an array and cuts every date range from it (the first rent, the period, the other currencies, the closing date, each loan's draws and repayments, the holding, the IRR inputs).
- [x] The refinance set comes from the same array (`private.refinance_transactions_in`); `private.refinance_transactions`, which `get_property_return_lines` calls, reads the lines once, and none when the property has no loan in the currency.
- [x] pgTAP parity: a copy of the old body is the oracle; the whole JSON is equal for a property with a refinance, one with hard-money draws and one with neither (year, quarter, default range, empty ranges).
- [x] Counted locally with `track_functions` on a scratch fixture of 1,800 other company lines (the script is not committed): `property_lines` calls per answer 12, 11 and 9 before, 1 after.

**Acceptance:** same answers (the parity test); fewer `property_lines` reads; the production time after the deploy is Flow QA's to measure.
