# FLOW-1168 · Jobs: a `sync_bank` that never finishes, a tagging failure with no end, sends claimed before they are sent
- **Type:** BUG · **Status:** in-progress (this PR) · **Depends on:** [FLOW-1160](FLOW-1160.md)
- **Source:** the state machine read of 2026-11-10 ([map](../../tech/state-machines.md), FLOW-1160). Read in the code, not run: check each still happens on `main` first.
- **Files:** `supabase/functions/flow-mcp/tools_sync.ts`, `supabase/functions/_shared/jev_tag.ts`, `_shared/push_send.ts`, `_shared/invite_email.ts`, `_shared/thread_purge.ts`, their tests; a migration if a job's end state needs a column.

- [x] `sync_bank`: a refused `mcp_sync_bank_finish` is not noticed (the call returns a status, it does not throw), so the job reads as running until it goes stale; a page-capped pull is stored as a finished success; `skipped` and 429 both read as `unavailable`.
- [x] Jev tagging: the 60-second rate gate is spent before the lease, so a run answered `busy` still blocks the next; the 180-second lease is never renewed while the work's own 120 seconds start after the listing; a failure that can never pass (`invalid_request`) retries every day and spends a call; a line can keep both a suggestion and a failure row.
- [x] Push: a new-line or weekly send that fails or runs out of time is lost, because its mark moved at the claim; a test claim is spent with no device; a malformed endpoint is deleted as gone.
- [x] Invite email: the claim (3 per invite) is spent before the send, so a failed send uses one.
- [x] Thread purge: a listed name that fails the path rule stays listed for good.

**Acceptance:** a function test per box; each job's states are a table per decision 0266.

**In #1125:** a refused `sync_bank` finish is logged; a tagging run answered busy does not spend the rate gate; a line keeps no failure row beside a suggestion that could not be removed. **Left, needs SQL:** a terminal state for a tagging failure that can never pass; a release for the push and invite-email claims when the send fails; an offset for the thread purge. **Left, a contract change:** `sync_bank`'s stored result has no field for an incomplete pull.

**In this PR:** one migration (`jobs_end_states`) and the edge functions, each flow a `defineMachine` table (`jevRun`, `pushClaim`, `inviteSend`, `purgeName`, `syncJob`). Jev: a line Jev refuses as invalid (HTTP 400 or 422, or the request failing its own check), in a run where Jev answered another line, is marked refused (`jev_line_failures.refused_at`, a 30-day wait tied by `jev_line_failures_refused_chk`) and is not sent again until a column its request is built from changes (the trigger `transactions_jev_refusal_reset`), the model version changes, or 30 days pass; a rate limit, an overload, a timeout, a 5xx or a key problem is never a refusal. `get_jev_status` adds `lines_not_retried`. The run renews its lease before each Jev call and stops when it lost it; its 120-second budget counts from the lease; the rate gate is spent only when the run starts tagging, so a run with nothing to tag leaves it. Push: `push_claim_targets` returns each claim and `push_release_claims` gives back a new-lines or weekly claim no device took when a try can pass later (a user one device took it from keeps it: no second push); a given-back weekly summary is tried again until 11:59 that Sunday (`weekly_released_on`); a test claim no device took is given back (`release_push_test`); an endpoint that is not a push service's, and any 4xx but 404, 408, 410 and 429, is `refused`, never deleted as gone. Invite email: a send Resend answered with an error gives its claim back (`release_invite_email`); a timeout keeps it, so an invite gets at most 3 real emails. Thread purge: a listed name the purge cannot remove is recorded (`thread_files_purge_skip`) and left off the list for a day, so the run goes on past it; the path rule stays. `sync_bank`: a done job says `complete` (false when the pull did not read everything), a retry says its `reason` (`busy`, `rate_limited` with `retry_at`, `unknown` once stale), the job's own token finishes it after a revoke, and flow-mcp tries a finish that was not stored once more. **Left:** a push run killed between its claim and its give-back leaves the claim spent (at most once, as before); a `sync_bank` finish lost twice (the database out of reach) leaves the job running for its 5 minutes; a Jev refusal is not cleared by a change to the company's projects or categories (only by the 30 days).
