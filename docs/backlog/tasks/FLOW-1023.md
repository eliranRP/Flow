# FLOW-1023 · Review's first card does not wait on its follow-up reads
- **Type:** SMALL CYCLE (perf) · **Status:** ready · **Source:** the perf steward's daily report ([2026-11-03](../../qa/perf/2026-11-03.md)), decision [0230](../../decisions/0230-screens-data-in-half-a-second.md).
- **Files:** `app/src/screens/review-queue.tsx` (the card's follow-up reads), `app/src/use-review.ts` or the card's read hooks, their tests.

With FLOW-1020 in production (2026-11-03), Review's list read starts about 90 ms after the tap and ends by about 0.7 s on the FLOW-804 phone. Review tapped as soon as Home shows its data still took 0.8 to 4.7 s to settle, p50 2.8 s over 6 runs. In the one slow trace (1,983 ms; the 2.3 to 4.7 s runs were not traced), the time after the list is likely the first card's own reads, started after the list lands:

- `review_anomalies`, `transaction_thread_counts`, `get_line_meta` and `get_line_split` start together at about 0.8 s.
- `company_integrations` starts at the same time. `jev_suggestions` and `tag_suggestions` start once it ends, so they may wait on it (not checked in the code).
- `jev_prefills`, `projects` and `categories` start after those.

Each step likely costs a round trip on 4G (not measured step by step), and each answer may change the card.

- [ ] Find which of these reads the card needs before it is useful, and which can fill in after; measure each step's cost first.
- [ ] Start the card's reads that do not depend on each other at once, and with the list where their arguments are known: the first page's transaction ids are known when its read answers.
- [ ] The card shows its main content (party, amount, date, the approve button) without waiting for the badges.
- **Acceptance:** unit tests that the card's reads start together; the steward's before and after on the FLOW-804 phone, Review tapped right after Home.
