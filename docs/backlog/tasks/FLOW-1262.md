# FLOW-1262 · CI: the get_project speed test does not fail on a slow runner, and names the state when it is slow
- **Type:** SMALL (CI test) · **Status:** in-progress (#PR) · **Source:** the perf steward's 2026-11-23 [report](../../qa/perf/2026-11-23.md), diff review (indexes, separate item); main's push run for #1245 on 2026-11-22.
- **Files:** `supabase/tests/database/project_page_speed.test.sql`.

Test 3 ("get_project on 2,100 lines stays fast with no planner statistics", under 3 s) took 0.16 s, 1.88 s, 1.90 s and 6.06 s on four CI runs with the same database code; the 6.06 s run failed main's push run for #1245 (an app-only change) and passed on its one re-run. The index reviewer's reading: the test runs as file 252 of 347, after files that insert and roll back, so the tables' statistics and bloat are in one of several states that depend on where autovacuum fell; with the row estimate clamped to 1, a per-line probe can pick a company-led index and read the company's 4,260 legs or 600 allocations per line (measured on production with index scans disabled: 5.8 ms by index against 2,228 ms by seq scan for one probe). The test guards against the n-squared plan, which took about four minutes.

- [x] Raise the limit from 3 s to 30 s (an 8× margin under the four-minute n-squared plan, and above every observed run).
- [x] Add a `diag` beside the time with `reltuples`, `relpages`, `pg_relation_size` and `last_autoanalyze`/`last_autovacuum` for `transactions`, `legs`, `allocations` and `accounts`, so the next slow run names its state.
- [ ] If the diag output later shows one probe flipping, file the function fix (read the project's legs and allocations once, as `pl_rows` does) as its own task.

**Acceptance:** the test still fails on the n-squared plan, passes on the observed runs, and prints the tables' state.
