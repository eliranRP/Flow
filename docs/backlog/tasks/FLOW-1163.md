# FLOW-1163 · Refresh queue and connections: a skipped run uses up the request, `forced` is dropped, claims are not per slot
- **Type:** BUG · **Status:** done (#1126, #1197, #1198) · **Depends on:** [FLOW-1160](FLOW-1160.md)
- **Source:** the state machine read of 2026-11-10 ([map](../../tech/state-machines.md), FLOW-1160). Read in the code, not run: check each still happens on `main` first.
- **Files:** `supabase/functions/mercury-sync/index.ts`, `supabase/functions/sumit-sync/index.ts`, `supabase/functions/mercury-connect/index.ts`, a new migration (+pgTAP) for `claim_connector_refreshes`, `note_connector_rejection`, `note_connector_failure`.

- [x] A run that answers `skipped` (the quiet gap, no chosen accounts) leaves its refresh request claimed, so the request is spent without a sync.
- [x] The cron drain passes `forced: false` whatever the request says, so a forced refresh inside the quiet gap is dropped.
- [x] Nothing closes or deletes a claimed request; the rows pile up.
- [x] `claim_connector_refreshes` and `note_connector_rejection` match on company and provider only: one claim stamps every Mercury slot and one rejection holds them all. Closed as designed: the queue is per company and provider because mercury-sync syncs every slot in one run, so a per-slot claim would split one run in two; `note_connector_rejection` had no caller and is dropped.
- [x] `note_connector_failure` overwrites `last_error`, so a passing failure after `auth` reads as connected again without a reconnect.
- [x] Mercury connect clears the cursor and the account choice before the new key is stored; a failure between the two stops the old connection.
- [x] SUMIT has no resumable cursor: a company past 20 pages fails with `sync_page_cap` on every run.
- [x] The claim's 10-minute window is a literal in three places; `cron_claim.ts` still says 15.

**Acceptance:** pgTAP for the claim and the two notes per slot; a function test per box; the map's rows updated.

**In #1126:** a request is `queued`, `claimed` or `finished` (deleted), moved by `settle_connector_refresh`: a run that threw or found the connection busy goes back to the queue; one that synced, or skipped for a reason a retry cannot change, finishes it; a request whose run died lapses at the next claim. The claim returns `forced` and both drains pass it on. An `auth` stop survives a later failure or rejection. The claim window is one private function for the claims. **Left:** per-slot claims (the queue is per company and provider by design, and mercury-sync syncs every slot in one run; `note_connector_rejection` has no caller); Mercury connect's clear-then-store (the safe fix is one transaction: a reset flag on `replace_connector_connection`); SUMIT's resumable cursor (a feature); the window literal in `connector_connection_status`, `sumit_status()` and `private.mcp_bank_connection_json`; `stamp_connector_sync` clearing `auth` in a race, and SUMIT's `note_sync_failure` overwriting it.

**In this PR (the leftovers):** one migration, `20261115180000_connector_leftovers.sql`. (1) `replace_connector_connection` takes `p_reset` and `p_kept` and resets the cursor and the account choice in the statement that stores the key; `mercury-connect` makes that one call (`_shared/connectors/mercury/replace_key.ts`) and, while the database has no `p_reset`, clears first and stores second as before. (2) `connector_connection_status`, `sumit_status()` and `private.mcp_bank_connection_json` read `private.sync_claim_window()`; `cron_claim.ts` and both `CLAIM_MS` already said 10, so no edge code changed. (3) `note_connector_rejection` had no caller and is dropped. (4) An `auth` stop clears only on a reconnect: both sync functions refuse a stopped connection before they run, so no sync can succeed with a key that was found bad, and a stamp that finds `auth` is a run that began before the stop. `stamp_connector_sync` and `stamp_sumit_sync` keep it (the time is still stamped and the claim freed), and SUMIT's `note_sync_failure` and `note_sumit_rejection` keep it with no retry time. (5) Per-slot claims are closed as designed (above). pgTAP: `connector_leftovers.test.sql`; Deno: `replace_key_test.ts`. **Left:** the SUMIT resumable cursor (a feature, built separately).

**In #1198:** SUMIT's pull resumes past the 20-page cap (`sumitPull`; `settings.pull` written with the documents by `upsert_sumit_window`; the finishing run stamps the sync; the owner's refresh calls again while the answer is partial, up to 10 calls a tap). Only a window listed whole in one run sweeps, so a company past the cap never has a deleted SUMIT document removed automatically (the trade for never removing a real one: SUMIT's list has no stable order). No bound fails a run: receipts past 1,000 waiting are stored with the company VAT rate and not re-rated, and a last row with no id makes the next run start over and count toward the 3-run stop. **Left on purpose:** a document that crosses the resume boundary with the anchor row in place is missed until a later window; a partial run waits for the next sync instead of requeueing itself.
