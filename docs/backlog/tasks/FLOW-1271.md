# FLOW-1271 · Perf: Profit's first view in one wave
- **Type:** MEDIUM (perf) · **Status:** in-progress (#1268) · **Source:** decision [0271](../../decisions/0271-half-second-by-kept-data-and-one-wave.md), item 3: the perf steward's plan; the perf steward's split of 2026-11-23.
- **Files:** `app/src/screens/company-profit-screen.tsx`, `app/src/use-company-profit.ts`, `app/src/company-next-month-query.ts`, tests.

Decision 0271, item 3. Profit sends 12 (year), 20 (month) or 26 (by date) requests in 2 waves (2026-11-23 split; 1.9 to 2.1 s). Wave 2 is gated on first paint: the project breakdowns (`get_breakdown` ×2 by project, income and expense, use-company-profit.ts:372-375, `useAfterFirstPaint(figuresIn)`) and the next-month card (`company_next_month_inputs` 127 KB, `loans`, `loan_balances`, `list_categories`, `expected_months`; the gate `useAfterFirstPaint(long ? yearsData != null : model != null)` at company-profit-screen.tsx:164, read by `useCompanyNextMonth`). The comment there (FLOW-1080) records why: the next-month reads wait so they do not share the link with the figures' own reads.

- [x] Keep the owner's order (FLOW-1080, 2026-11-07, "Keep it"): the next-month card reads after the figures. Changing it needs the owner's go with a measurement.
- [x] Decide per read whether it is in the first view of each Profit view: the month by project (the default, `/profit`), the month by date (`?by=date`), the month's other orders, and the year and since-the-start periods (`?period=year`, `?period=all`); the split measured the month by project (`/profit`), the month by date (`?by=date`) and the year (`?period=year`); not measured: the month by category (`?by=category`), by amount (`?by=amount`), and since the start (`?period=all`). The project breakdowns that wait for first paint are not drawn in the by-date view; say per mode whether any first-view read still waits, and start it at mount.
- [x] Wave 1 holds 8 reads on the 4G pipe in the by-date view (`companies`, `get_profit_months`, and `get_dashboard` (month and year to date), `get_breakdown` by category and `get_breakdown_lines` (income and expense each) twice each): measure whether fewer, combined reads would draw the figures sooner, and file what would need a database change as its own task.
- [x] Tests: the first-view reads of each mode start in one wave; the figures are unchanged.

**Acceptance:** Profit's first view loads in one wave in every mode; data shown falls on the FLOW-1276 sweep; the figures do not change.

**Found, per view** (a local production build against the stub backend, phone profile; reads by when they go out):

- **Month by project (`/profit`):** every first-view read goes out at mount (the company's row, the month's and the year's `get_dashboard`, both project breakdowns, the chart's `get_profit_months`); only the next-month card's five reads follow the figures (FLOW-1080, kept). Nothing to start earlier.
- **Month by date and by amount:** the category breakdowns and the two `get_breakdown_lines` go out at mount. The project breakdowns, not drawn in these orders, go after the first paint and stay there: starting them at mount adds two reads to the first wave for rows nobody sees. On a cold load the lines wait one round trip for the company currency, which a null `p_currency` cannot replace without a database change: FLOW-1290.
- **Month by category:** the breakdowns go out at mount; a category's lines are read once its row is near (FLOW-1194), which needs the breakdown's category ids, so they cannot start earlier. The one-read-per-direction answer the date order uses would send every line of the month for rows below the fold.
- **Year and since the start:** `get_profit_months` goes out at mount and holds everything the figures need. The year's project list (`list=project`) read its two project breakdowns for this year until the years' read said the asked year exists, then again for the asked year: a past year sent four reads in two waves. They now go out for the asked year at mount (`forecastYear`), two reads in one wave.
- **Fewer, combined reads:** the wave's reads leave together and are small (7 to 16 KB each, FLOW-1080), so on the 9 Mbps link the eight take about 70 ms of transfer in all; a combined read would save only the requests' headers and would wait for its slowest part. No combined read is proposed.

**Measured** (the same setup as FLOW-1278; the month by project, medians of 7): the first in-app visit is unchanged, as its reads already left together (868 ms to no skeleton and the figure, against 783 on `c48f453`: the same code for this view); the past-year project list reads 2 requests in one wave instead of 4 in two (stub run).
