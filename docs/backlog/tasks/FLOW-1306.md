# FLOW-1306 · Perf: the loan schedule in the database, kept current on every loan write
- **Type:** LARGE (perf) · **Status:** ready · **Source:** the FLOW-1275 [plan](../../tech/flow-1275-server-side-math.md), slice 3 (owner approval 2026-11-24).
- **Files:** a migration `<ts>_flow_1306_loan_schedule.sql` (`private.loan_schedule`, `public.loan_schedule_rows`, `public.loan_schedule_meta`, RLS, triggers on `loans` and `loan_rates`, backfill); `packages/shared/fixtures/vectors/loan-schedule/*.json`; pgTAP `flow_1306_loan_schedule.test.sql` and the generated vectors file; a vitest file for the vectors. No app change.

The forecast and the Loans list build every loan's schedule on the phone (`buildLoanSchedule`). Its inputs are the loan's terms and rates only, which change rarely (no write to `loans` or `loan_rates` in production since 2026-11-21), so it is kept in a summary table rebuilt by triggers in the same transaction. A plpgsql build costs about 1.6 ms a loan (measured read-only as Flow QA).

- [ ] `private.loan_schedule(p_terms jsonb)`, immutable: every kind, rate changes and recasts, balloon and final adjustment, the exact annuity in `numeric`, interest half to even; refused terms give an error code, as the app's schedule throws.
- [ ] The table and its meta row per loan, RLS (`readable_company_id`), no write grant to `authenticated`; triggers on `loans` (insert, delete, update of a term column or the status) and `loan_rates` (insert, update, delete); a backfill.
- [ ] Vectors exported from every case of `loan-schedule.test.ts`, equal row for row in vitest and pgTAP; a pgTAP case per write path.

**Acceptance:** every vector equal; after any loan or rate write the table equals the function of the new terms in the same transaction; the trigger's time per loan measured on a local database.
