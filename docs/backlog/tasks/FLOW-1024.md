# FLOW-1024 · On iPhone a sheet with a field rises off the top of the screen when the keyboard opens
- **Type:** BUG · **Status:** claimed (the FLOW-1024 PR) · **Source:** the owner, 2026-11-03, with iPhone screenshots: a money sheet on a property's investment page, the field focused, the sheet's top above the status bar ("I see this happen in multiple places for inputs").
- **Files:** `app/src/ui/sheet.tsx` (Vaul's `repositionInputs` off), `app/src/ui/css/08-tabbar-empty.css` (`.ui-sheet-panel` sits on `--kb`), `app/src/ui/css/02-fields-sheets.css` (the overrides of Vaul's inline height go), `app/src/ui/keyboard-inset.ts` (`clearDrawerLift` goes), `keyboard-inset.test.tsx`, `app/e2e/review-keyboard.spec.ts`.

Cause: Vaul lifts an open drawer above the keyboard by `innerHeight - visualViewport.height`. iOS Safari keeps the layout viewport with the keyboard up and also pans the visual viewport down to the focused field, so the sheet rose by the keyboard and again by the pan, off the top.

- [x] Vaul no longer moves the sheet (`repositionInputs={false}`). The panel's `bottom` is `--kb`, the space below the visual viewport, which `useKeyboardInset` updates on every resize and pan: the sheet ends where the view ends, above the keyboard, panned or not.
- [x] The Vaul workarounds this leaves unused are deleted: `clearDrawerLift`, its test, and the `!important` height overrides.
- **Acceptance:** an e2e test with a stand-in iOS visual viewport (keyboard up, then panned): the sheet ends at the view's bottom. It fails on the old code (200px too high, the pan). The Android-style keyboard specs still pass.
