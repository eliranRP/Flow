# FLOW-1344 · Perf: at most four database reads in flight at once, so a cold Home no longer wakes every database backend together
- **Type:** SMALL (perf; part of FLOW-1300) · **Status:** in-progress (#1313) (the owner's go, 2026-11-27: "Build it, measure") · **Source:** the 2026-11-27 daily report's diff review; [FLOW-1300](#flow-1300), [the 2026-11-26 perf report](../../qa/perf/2026-11-26.md) section 5.
- **Files:** `app/src/lib/read-cap.ts` (new), `app/src/lib/read-cap.test.ts` (new), `app/src/lib/supabase.ts` (the client's `fetch` option), `app/src/lib/company-header.test.ts`, `app/src/lib/supabase-wiring.test.ts` (new).

The Nano database is out of memory (RAM full, swap about RAM). Each Postgres backend grows to about 23 MB after a few distinct reads, PostgREST runs about 7, and a cold Home sends 23 to 24 requests in 4 waves, waking all of them at once; reads then stall for seconds. The app's Supabase client now lets at most 4 REST/RPC requests (`/rest/v1/`) run at once (`MAX_REST_IN_FLIGHT`, one constant in `read-cap.ts`); the rest wait first in, first out. Auth, storage, edge functions and realtime are not capped. A slot frees when the response headers arrive. An aborted queued request leaves the queue and rejects with an AbortError without being sent. No retries. The company header is set before the queue, so a request queued while the user switches company still names the company it was issued under.

- [x] Build the cap in the client's custom `fetch`, with unit tests and a 23-parallel-`rpc` test.
- [ ] Measure: the next sweeps (the steward).

**Acceptance:** the next sweeps show fewer multi-second stalls and no worse stall-free times.
