# FLOW-1194 · Perf: Company profit's "by category" order loads category lines on scroll; search finds every line
- **Type:** MEDIUM (perf) · **Status:** in-progress · **Source:** the perf steward's daily diff review, 2026-11-14 ([report](../../qa/perf/2026-11-14.md), finding 9).
- **Files:** `app/src/use-company-profit.ts`, `app/src/screens/company-profit-screen.tsx`, `app/src/screens/profit-categories.tsx` and their tests; `app/src/search.ts` (`searchRowDetails` moves in from the search screen); `app/src/ui/screen-skeletons.tsx` (one loading row).

In the "by category" order, the first view shows collapsed category rows, with each count and amount from the two breakdowns. Yet one `get_breakdown_lines` loop runs per category, all categories in parallel (`use-company-profit.ts:290-296`), each paging 40 rows a call in sequence (`:223-242`). That is about 20 calls for a month with about 20 categories. The count comes from the code path, not a trace.

The owner was asked first, because users could see a short load.

**The owner's answers, 2026-11-14.** To the card "Company profit's \"by category\" order loads every category's lines up front, even though they start collapsed: about 20 extra reads for a month with ~20 categories. Loading a category's lines only when you tap it would make the screen faster, but a short loading row shows each time a category opens. Do you want that?", the owner first chose "Load on tap (Recommended)", then wrote: "Load on scroll" and "And the search ahould include them also". Then, again: "Load on scroll".

**The owner's answer, 2026-11-14, to the second card.** The card asked: "FLOW-1194: Company profit has no search field today. When you said \"the search should include them also\", which search did you mean? (The app's main search already asks the server, so it finds every line.)" The owner chose "Add one to profit (Recommended)" ("A search field on Company profit that asks the server, so it finds lines whose category hasn't loaded yet.").

- [x] Entering the "by category" order reads no lines. A category's lines are read as its row scrolls into view, so they are usually ready before it is tapped (unmeasured: no trace has timed it). If a tap comes first, the lines are read on the tap, with a short loading row. Each category is read once (the React Query cache keeps it).
- [ ] The date and amount orders read all lines with one paged read and a larger page, not one loop per category. Not done: `get_breakdown_lines` has no form without a category (it needs a group key, or the kept-out flag), so one read of every line needs a new migration. These orders keep the one loop per category, which now reads only the counted lines (they never drew the kept-out ones). Follow-up: a migration that lets `get_breakdown_lines` read a direction with no group key.
- [x] Search includes lines not loaded yet. Company profit's month view has a search field that asks the server (`search_transactions`, scoped to the month), never only the rows already loaded. The owner chose to add it (the second answer above). A test pins that a line from a category that never loaded is found.

**Acceptance:**
- Entering the category order reads no lines. Scrolling a category into view reads its lines once.
- A line in a category that never scrolled into view is found by the search field on Company profit, which asks the server (`search_transactions`).
- The PR's traces show the before and after.
