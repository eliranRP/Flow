# FLOW-1280 · Plan: cold Home's start-up, where FLOW-1116's early reads did not help
- **Type:** PLAN FIRST (perf) · **Status:** plan-first · **Source:** decision [0271](../../decisions/0271-half-second-by-kept-data-and-one-wave.md), item 4: the main-thread profile of 2026-11-23 ([2026-11-23-main-thread.md](../../qa/perf/2026-11-23-main-thread.md#cold-home)); FLOW-1274.
- **Files:** A plan in `docs/tech/`; no build before the owner approves. The plan names the files a build would change.

On the FLOW-804 phone, cold Home's first `/rest/v1` read leaves at a median of 715 ms, 196 ms after the entry (about 203 KB gzipped JavaScript and 43 KB of CSS) has downloaded, and the figures show at about 3.2 s. The profile shows the read waiting for the app's code to run: module evaluation (28 to 72 ms), the session restore and `startHomeReads`.

This is the idea of [FLOW-1116](FLOW-1116.md), which was **built and dropped on 2026-11-14**: an inline script in `index.html` sent the two reads before the app's code arrived. It cut the first read from 801 to 234 ms, but the cash figures only moved from 1,489 to 1,429 ms (faster in 10 of 15 runs), because the figures wait for the app's own start-up, not for the data. The owner chose to drop it and to shrink Home's start-up instead. FLOW-1274 found nothing that overturns that, and no measurement here shows that the figures would show sooner; it only shows when the first read leaves. So this task is not ready: it needs the owner's go.

What the plan must answer before any build:
- What is different from FLOW-1116: why the figures would now show sooner, given that start-up was the bottleneck then. The profile's start-up parts are the entry's evaluation (28 to 72 ms), the session restore and the first React render; the plan says which of them it would shorten, with a measurement of when the figures show.
- The cheaper options the profile found first: the formatter warm-up (done in FLOW-1274, the first read 88 to 111 ms sooner), and a smaller entry (246.5 of 248 KB, so every KB Home needs delays everything).
- How the early reads' session, company header, expiry and CSP hash would work, as FLOW-1116's plan answered them.

- [ ] A written plan with the measurement of figures shown (not the first read's time) before and after a prototype, on the FLOW-804 phone profile.
- [ ] The owner's go, in the task.

**Acceptance:** the plan is approved by the owner, and if built, the cold-Home figures show at least 300 ms sooner on the phone profile (the time the data is drawn, as `load-report` and the steward's cold loads measure it), with the same figures and the bundle within budget. The time the first read leaves is not an acceptance.
