# FLOW-1042 · Pull to refresh: the whole screen comes down, and a pull brings new data
- **Type:** SMALL UI · **Status:** done (#979) · **Depends on:** FLOW-1039 (#977) · **Source:** the owner, 2026-11-05, after FLOW-1039 went live: a pull should feel like pulling the whole screen down, its colours too (on Home the purple band stretches down), not a spinner over a still screen; and a pull does not seem to bring new data. Answers FLOW-1040's first box: a pull asks for a bank sync.
- **Files:** `app/src/ui/pull-refresh.tsx` and its test and story, `app/src/ui/css/62-pull-refresh.css`, possibly the app shell in `app/src/App.tsx` (the element that moves), the refresh's bank calls (`app/src/edge.ts` callers: `mercury-sync`, `sumit-sync`), `docs/design/log/2026-11-05-flow-1042.md`, `docs/changelog.d/2026-11-05-flow-1042.md`, `docs/backlog/tasks/FLOW-1040.md` (its first box done).

**Why a pull brings no new data today:** `refetchQueries({ type: "active" })` re-reads only the reads on screen. Reads are fresh for 30 minutes (`query-client.ts`), so a read nested in another (`client.query({ ...staleTime })`, for example the month forecast's open invoices) and every other screen's reads come back from the cache. And no bank sync starts, so new bank lines arrive only with the server's own schedule.

- [x] **The screen comes down.** While pulling, the routed screen itself (everything under the top safe area, the tab bar stays put) moves down with the finger, with resistance, and the gap above it shows the colour of the screen's top: the band's colour where the screen starts with a band (Home, a project), the page background elsewhere. The spinner sits in the middle of the gap. Released past the threshold, the screen rests a little down (the gap holds the spinning mark) until the refresh ends, then slides back up; released before, it springs back. Nothing overlaps the screen's own controls any more.
- [x] **A pull brings new data.** A refresh re-reads Flow's own data from the server: it marks every cached read stale and refetches the ones on screen (`invalidateQueries()`, so nested reads and the other screens read again too), and the mark spins until those reads are back (400ms at least). It starts no bank sync (the owner, 2026-11-05: "It should refresh the data from flow server."), so `mercury-sync` and `sumit-sync` are not called and there is no 8-second cap.
- [x] A failed read shows one toast, as today. Reduced motion: no follow and no spring; the screen does not move, the mark fades in.
- [x] The gestures FLOW-1039 keeps out (sheets, swiped rows, edges, scrolled lists, fields) stay out.
- **Acceptance:** unit tests that a refresh invalidates every read (a nested fresh read reads again) and calls no sync (the owner's change, 2026-11-05); the story shows the screen moved with the band colour in the gap at 320 and 393, both themes; a design log entry.
