# FLOW-1348 · Perf: the read queue drops reads nobody waits for, lets writes go first, and frees a hung request's slot
- **Type:** MEDIUM (perf; part of FLOW-1300) · **Status:** ready · **Source:** the [2026-11-28 daily report](../../qa/perf/2026-11-28.md), diff review (load scope, row 3); #1313 review round 1, note 1.
- **Files:** `app/src/lib/read-cap.ts`, `app/src/lib/supabase.ts`, Home's read hooks (pass React Query's `signal`), `app/src/signalled.ts`, their tests.

Since FLOW-1344 at most 4 requests run at once. A queued request leaves only on abort, and on Home only the forecast reads pass a signal (elsewhere the Jev review reads, `use-review.ts`, do too), so after a tab change, a month step or a company switch the old screen's queued reads still go out, ahead of the next screen's reads and of writes, which wait in the same queue: up to about 14 dead reads (1 to 1.4 s) when the tap comes while a cold Home drains. The client also sets no request time limit, so a request that never answers holds a slot until the browser gives up, and four of them stall every later read and write.

- [ ] Pass the query's `signal` to the reads of Home (and the other many-read screens: the project page, Review, Profit by date), so a cancelled query leaves the queue.
- [ ] Writes (user saves) are not queued behind reads; say in the PR how a write is told apart from a read RPC (both are POST).
- [ ] A time limit per request (for example the client's `db.timeout` or an abort timer in the cap) that frees the slot; pick it above the database's 8 s `statement_timeout`.
- [ ] Tests for each.

**Acceptance:** a tap or a save made while a cold Home drains is not delayed by the old screen's reads; a hung request frees its slot; the project page, Review and Profit by date are back to 11-27's fresh-data times or better (with FLOW-1346, this carries FLOW-1344's "no worse stall-free times").
