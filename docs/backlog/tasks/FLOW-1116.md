# FLOW-1116 · Plan: Home's figure reads leave from the page itself, before the app's code arrives
- **Type:** PLAN FIRST (perf) · **Status:** dropped (the owner, 2026-11-14) · **Source:** the perf steward's daily report ([2026-11-09](../../qa/perf/2026-11-09.md)); the owner's pick 2026-11-09: "Plan it first".
- **Files:** to be named by the plan; likely `app/index.html` or a small inline script, `app/src/home-early-reads.ts`, the security headers (CSP).

Since FLOW-1115, a cold start on Home sends its two figure reads (`cash_months`, `get_dashboard`) once the app's code has loaded and run its first module: the first read at about 0.8 s on the FLOW-804 phone. The page itself arrives at about 0.15 s and the code at about 0.55 s. A small script in the page could send the two reads at about 0.2 s and hand their answers to the app, which could save about another 0.5 s on a cold open (not measured).

The plan, for the owner before any build:
- How the script reads the saved session without the Supabase client: an expired access token, the refresh, and a session that belongs to another user.
- The company header (`x-flow-company`) and the shown company, as the app sends them.
- How the answers reach the query cache with Home's keys, and what happens when a read fails or arrives late.
- The CSP: an inline script needs a hash or nonce (decision 0192).
- How it is measured: the steward's local A/B of cold Home on the FLOW-804 phone, and the same read count.

**Built and dropped, 2026-11-14.** The owner's go, 2026-11-14, to the card "FLOW-1116, cold Home (3.1–4.2 s to data today on the phone profile): start Home's figure reads from the page itself, before the app's JavaScript arrives, so data and code load at the same time. It adds a small inline script to index.html and a hand-off to React Query. Should I build it?": "Build it (Recommended)" ("Build behind the gates and measure cold Home before/after on production; keep it only if faster."). Then the card: "FLOW-1116 (cold Home early reads) is built but the gain is small: on a simulated phone the data request leaves ~570 ms earlier, yet the figures show only ~60 ms sooner (1,489 → 1,429 ms median), because the app's own code start-up is the bottleneck. It adds an inline script that copies Home's default-period logic, plus a hand-off layer. Production isn't measured yet. What should I do?"

Answer: "Drop it (Recommended)" ("Not worth the extra script and duplicated logic for ~60 ms; note the finding (code start-up is the bottleneck) and look at shrinking Home's start-up instead.")

Design tried: an inline script in app/index.html started cash_months(p_months 4) and get_dashboard(default period) with the stored session; app/src/early-read.ts handed the parked answers to useCashMonths and dashboardQueryOptions when args, company, user and age (<30 s) matched.

Measured (perf stub backend, 300 ms per read, phone profile, 15 paired runs): first read leaves 801 → 234 ms; cash figures visible 1,489 → 1,429 ms (faster in 10 of 15). The figures wait for the app's code to run, not for the data.

Next lever: shrink Home's start-up (entry JS 202 KB gzip, the first render), not the reads.
