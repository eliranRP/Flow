# FLOW-1234 · Perf: company_next_month_inputs stops rescanning the recurring charges' lines
- **Type:** SMALL (perf) · **Status:** in-progress (#PR) · **Source:** the perf steward's 2026-11-19 [report](../../qa/perf/2026-11-19.md), diff review row 2 (indexes and schema).
- **Files:** a new migration patching `public.company_next_month_inputs`, `supabase/tests/database/` (a parity test).

FLOW-1216 (#1219) made the `streams` CTE read `private.recurring_charge_lines_of_projects`. That function is security definer, so it is not inlined, and the planner runs the `not exists (select 1 from streams …)` as a nested-loop anti join that rescans the function's result (about 410 rows, joined to `projects`) 94 times, discarding 38,463 rows. The `entries` query took 67 to 83 ms this way; with `streams as materialized` it took 61 ms (read-only, as Flow QA).

- [x] Mark the CTE `as materialized` (an anchored in-place patch, each anchor matching once), and consider a `rows` estimate on the function.
- [x] pgTAP: the answer is unchanged for the test company.
- [ ] Measure the whole call before and after on production, read-only, as Flow QA.

**Acceptance:** same answer; `company_next_month_inputs` is faster by the measured amount (expected 6 to 22 ms); the tests pass.
