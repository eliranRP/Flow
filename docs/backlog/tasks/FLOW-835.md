# FLOW-835 · PR check under 100 seconds
- **Type:** INFRA · **Status:** done (#601) · **Depends on:** FLOW-832 · **Source:** FLOW-832 follow-up, measured on #594 on 2026-10-15: the `pr` check took 220 s on a shared-UI change. Per job: tests shards 73 s, 137 s and 151 s of test time (unbalanced), about 30 s of container init, a 15 to 18 s "Post Run actions/setup-node" cache save inside the Playwright container; static about 105 s.
- [x] The `pr (tests)` matrix runs six shards (`--shard i/6`) instead of three. The `pr` aggregate job still needs every shard.
- [x] The PR runner jobs (`static`, `types`, `db`) restore the pnpm store read-only with `actions/cache/restore`, keyed like setup-node's cache on `pnpm-lock.yaml`, and set setup-node without `cache: pnpm`, so no job waits on a cache save in its post-step. `ci.yml` on main keeps saving the store. The container `tests` shards cannot read that cache and install cold (a few seconds).
- [x] The typecheck, and the unused-code and CSS checks it runs with, move out of `pr (static)` into their own job, `pr (types)` (`--part types` in `scripts/local-ci.sh`), so the two run side by side. The aggregate `pr` job needs `types` too.
- [x] Shard balancing: vitest 4.1.11 shards by a hash of each file's path, then cuts the list into equal file-count ranges, and sorts by duration only after that. A duration sort therefore cannot balance `--shard`. A custom sequencer would need a timing table committed to the repo, which goes stale, so the shards stay as vitest makes them.
- [x] The runbook (`docs/runbooks/ci-cd.md`), the backlog guide (`docs/backlog/README.md`) and the pins in `scripts/ci-cd.test.mjs` name six shards, the types job and the read-only store.
- [ ] **Acceptance:** the `pr` check of a one-line UI change and of a PR the size of #594 finishes in 100 seconds or less, measured in the Actions run times on the PR. Not met until a run measures it.
