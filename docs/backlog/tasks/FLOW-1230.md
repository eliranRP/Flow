# FLOW-1230 · Perf: the project page's second wave of reads starts a hop earlier and carries two reads fewer
- **Type:** SMALL (perf) · **Status:** done (#1220) · **Source:** the perf steward's re-measure after #1217, 2026-11-18. On the FLOW-804 phone profile against production, an in-app visit from Home to `/projects/:id` settled at 2758 ms (decision 0230: 0.5 s). The first wave (both `get_project` reads, the cash months, the changed charges, the month row) ran from 127 to 1413 ms; a second wave of eleven reads began at 1394 and ended at 2707, and the last skeleton, the forecast row, cleared then.
- **Files:** `app/src/screens/project-detail-screen.tsx`, `app/src/screens/project-menu.tsx`, `app/src/screens/project-page-forecast-start.test.tsx`, `app/src/screens/books-states.test.tsx`, `app/src/screens/project-menu-figures.test.tsx`.

What the measurement showed (a local build against production, same profile, alternating runs of main and the branch): starting the forecast's reads with the first wave (at navigation, before any `get_project` lands) delayed the first data by about 270 ms and settled only 110 ms sooner, because nine more requests then compete with the page's own reads on a 4G line and a slow CPU; that was dropped. Two smaller changes kept:

- [x] The ⋯ menu's group reads (`list_project_groups` and the project's `group_id`, the "/projects" request) are read only when the ⋯ button is touched (FLOW-1212's prime), or when the menu or the edit sheet opens. Only the edit sheet shows the קבוצה row, two taps after the button, so the page's second wave carries two reads fewer.
- [x] The forecast's reads start when either of the page's two `get_project` reads lands (the page's own, or the lifetime read, which is the same function over every period and often answers first), not only the page's own. The overhead hint comes from whichever landed. The page still draws from its own read; the forecast's figure still waits for the lifetime read.
- [x] Tests: the reads start with only the lifetime read landed (a project and the overhead project); the groups are not read at the page's first paint and are read on the button's touch. They fail on main.
- [ ] Not done here (proposal in the PR): the second wave is still eight reads (`companies`, `expected_months`, `project_category_months`, `project_forecast_edits_for`, `loans`, `loan_balances`, `forecast_overrides_for`, `list_categories`), the page's settle time. One RPC for the project's forecast inputs (as `company_next_month_inputs` is for the company) would make it one round trip; it needs a migration and pgTAP parity.

**Acceptance:** with the page's own read held back, the forecast's reads go out when the lifetime read lands; the groups are read on the ⋯ button's touch; the page shows the same rows and figures; the tests pass.
