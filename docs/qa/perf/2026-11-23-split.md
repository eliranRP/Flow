# Where a screen's time goes, 2026-11-23

The perf steward's split of an in-app visit to each main screen, for decision [0271](../../decisions/0271-half-second-by-kept-data-and-one-wave.md). Production `36cb136`, measured about 12:36 UTC, signed in as the Flow QA owner.

## Method

The FLOW-804 phone: 412×915 mobile viewport, CPU slowed 4× (`Emulation.setCPUThrottlingRate`), 85 ms latency, 9 Mbps down and 1.5 Mbps up. Each run uses a fresh browser context:
1. Open Home and wait until it settles.
2. Make an in-app visit to the screen (`history.pushState` and `popstate`, as a tap does).
3. Watch for 6 s.

The table gives the median of 3 runs per screen. Profit's rows are `/profit` (the month, in its default order by project), `/profit?period=year` and `/profit?by=date` (the month, ordered by date).

| Measure | What it counts |
| --- | --- |
| Settled | No skeleton or busy marker (`.ui-skeleton-bar`, `.ui-skel-row`, `.ui-skel-leaving`, `[aria-busy=true]`, and for the sweep `.ui-chart-skel`; the run's list also named `.ui-chart-skeleton`, which no element has, but a chart skeleton's bars carry `.ui-skeleton-bar`, so they were matched; the sweep uses `.ui-chart-skel`), and the page's last DOM change. Both are measured from the visit. |
| Main thread | The CDP `Performance.getMetrics` `TaskDuration` delta over the whole 6 s window. It is an upper bound, because it includes work after the page settles. |
| Network busy | The union of the Supabase REST request intervals that start before the settle point. |
| Waves | Groups of request starts more than 250 ms apart. |
| Requests | Every Supabase REST request, including duplicates. |
| KB | The encoded bytes received for those requests (CDP `Network.loadingFinished`), in one run. |

Each request count is for one run. It is higher than the number of distinct reads, because a screen's reads also include repeats, such as Profit's month and year-to-date `get_dashboard`. Settled, main thread and network busy are medians of the 3 runs; waves, requests and KB are from one run. The per-run values of the medians other than settled were not kept (FLOW-1276's script will print them).

These visits start after Home has settled, so the reads they share with Home (for example Recurring's schedule) are already cached. Neither a first visit (nothing cached) nor a kept-data visit is measured here; the first FLOW-1276 sweep sets the baselines of 0271's three times.

## Home

Cold Home, from the steward's post-deploy check on production `36cb136` about 04:35 UTC: 5 cold loads, each in a fresh browser context. The data was shown, with no skeleton left, at 3,128 to 3,446 ms (median 3,247). The first read left 772 to 853 ms after navigation began (`page.goto`), and each load made 25 reads. The same day's daily report, on `dc189b8`, gives a median of 3,491 ms.

## Round trips

`pnpm latency` at about 08:12 UTC on `36cb136`, 10 calls per read from the measuring machine: the median ranged from 155 ms (`list_categories`) to 382 ms (`company_next_month_inputs`). The daily report's run at about 01:15 UTC gives 157 to 394 ms. Separately, the slowest function takes about 140 ms in the database itself (`recurring_schedule`, 136.7 ms in the daily report).

The two runs differ in both directions, by up to 0.6 s.

Between them, #1252 and #1255 reached production. #1255 moved Home's late-bills reads to mount, and Recurring reads the same keys. The runs were also at different hours and machine loads. Three visits per screen do not separate these causes. One run is enough for 0271, because every screen misses 0.5 s in both runs.

The daily report's "data shown" column (the first figures drawn, or no skeleton) is earlier than either run's settled time, or about the same for Projects and the project page. Examples are Profit's month figures at 0.91 to 1.04 s and Review's first card at 0.81 to 1.12 s.
