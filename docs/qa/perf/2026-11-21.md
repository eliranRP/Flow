## 5. Diff review (`5bcdf48..8f1decf`, 5 commits: #1227 to #1231; the code changes are #1227, #1229 and #1230)

Three read-only reviewers looked at the diff, one lens each: load scope, response fields, and indexes and schema. Two of them measured on production as Flow QA, inside read-only transactions.

The diff is clean for every lens. The load-scope reviewer found two small things next to it:

| # | Screen or read | Finding | Saving | Size | Where |
| --- | --- | --- | --- | --- | --- |
| 1 | Project ⋯ menu, group move | A move waits for a refetch of everything under `"project"` (up to four requests on the project page) before its sheet closes, though it changes only `group_id`. Since #1229 the menu's current group comes from that `get_project` refetch. | the sheet closes about one round trip sooner | small | FLOW-1244 (a builder is on it) |
| 2 | Project ⋯ menu, groups read | Since #1229 the groups read returns the company's list and no longer depends on the project, but it is still keyed per project, so each project's first ⋯ touch reads the same list again. | 1 request per further project within the 60 s freshness window | small | FLOW-1245 (a builder is on it) |

Checked and fine:
- **Load scope:** no screen gained a request. The project path lost three: the forecast's `loans` and `loan_balances` reads (FLOW-1240) and the menu's `projects.select(group_id)` (FLOW-1243). The forecast uses the same lifetime `get_project` key that its four callers already hold, so no extra `get_project` is sent. Nothing reads `loans` or `loan_balances` for one project any more. #1227 adds no read.
- **Response fields:** `group_id` and the interest and escrow category ids have readers. `principal_category_id` and `fees_category_id` (about 57 bytes per loan while null) have none: the forecast files only interest and escrow. Too small to file; drop them the next time `get_project` is patched, app first. Since #1230 the project page fetches about 900 bytes less per loan in two fewer requests (the response-fields reviewer's measurement of the removed `loans` and `loan_balances` rows), against 115 bytes more per loan in each `get_project` answer. `docs/mcp/TOOLS.md`'s `get_project` entry does not list the four new loan keys (its `list_loans` entry does); FLOW-1244 adds them.
- **Indexes:** both migrations are live and add no index. The new keys come from rows `get_project` already reads, so there is no new join or scan. `get_project`'s reads use `loan_rates_company_loan_idx`, `legs_loan_idx` and `transactions_pkey`; `loans` is read by a sequential scan, which is right at 33 rows on 2 pages (every company's loans; Flow QA's are 22 of them). Four indexes on `get_project`'s tables have never been used (`projects_group_idx`, `loans_rate_index_idx`, `loans_refinanced_into_idx`, `loans_company_id_interest_category_id_fk_idx`), all older than the diff; three cover foreign keys. `loans`' row estimate is 16 for its 33 rows, which changes no plan at this size.
