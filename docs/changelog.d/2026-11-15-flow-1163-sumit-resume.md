**FLOW-1163 (SUMIT's resumable pull).** A SUMIT company with more than 20 pages (1,000 documents each) of documents used to end every run with `sync_page_cap`: the run listed 20 pages, threw before writing anything, and listed the same 20 pages again, so nothing past them was ever stored. `sumit-sync` now stores what a capped run listed and records where to continue (`connector_connections.settings.pull`: the next offset, the id of the row before it, the ids of the invoices the window's runs listed so far, the VAT rates a receipt needs from an invoice listed earlier, and any receipt whose invoice is not listed yet), and the next run, cron or the owner's refresh, continues there. It asks from the row before the continuation and checks it is the row the last run ended on; if rows were added or removed ahead of it the offsets no longer line up and the run starts over from the first page. A partial run does not stamp the sync and is not an error: the connection reads as it did, with no new wording, until a run lists the window to its end. The run that lists the last page stamps the sync, so the connection reads as synced. Only a window listed whole in one run sweeps, as before; a window that took more than one run never does, the finishing run included, because SUMIT's list has no stable order and a document no run listed could be one that moved between runs. So a company past the cap never has a deleted SUMIT document removed automatically; that is the trade for never removing a real one (a missed removal is recoverable, a wrong one deletes a line from the owner's books). Three runs in a row that leave the continuation where it was (the list shifted under it each time) stop the pull: the cron and an unforced run skip the connection, `sync_page_cap` shows as before, and the owner's own refresh still tries; a run that moves the continuation, or finishes, ends the count (`sumitPull`, decision 0266; the rule Mercury has since FLOW-1162). The documents and the continuation are one write (`upsert_sumit_window`, new; `upsert_sumit_documents` is the same function with the sweep on), so a run killed at any point leaves a continuation that never points past documents that were not stored. Deploy order: the edge function goes first; against the old database a run that would need the new function ends in `sync_page_cap` and writes nothing, as before, and a run that lists a whole window works as before. Tests: a fake SUMIT list in Deno (a 45-page window in three runs with every document stored once, no sweep on any run, nothing removed by a three-run window even for a stored document no run listed, the invoice-list bound, the repeated continuation, killed runs, the old database, an uncapped run as before, receipts listed before and after their invoice) and pgTAP for the SQL.
