**FLOW-1171 (perf queue).** The project page's read, `get_project`, does less work and sends less, with the same figures. `private.project_investment` called `private.line_in_cash` for every line, a SQL function Postgres cannot inline that re-reads the line (RLS checked) each time, and its direct branch read the whole company's lines. It now joins each line once, reads the owner's cash switch and the category from it, and reads only the project's own lines, as the shared branch does; `line_in_cash` has no other caller and is dropped. `get_project` gains `p_lines boolean default true`: the app asks with `false` and no longer gets the project's 40 newest lines, the category roll-ups, `excluded_categories_by_currency`, `pending_agorot` and `pending_other_currencies`, which no screen reads (the schema keeps them optional, so a saved answer still parses). flow-mcp and any caller that omits the flag get today's answer exactly. Measured on a local database with a synthetic 2,000-line company over 14 projects, as an authenticated owner, best of 5 per project: `project_investment` 726 ms to 4 ms a project (10.2 s to 59 ms for all 14); the whole `get_project` 679 ms to 48 ms with the default answer and 38 ms for the app's, whose answer is 2.6 KB instead of 14.7 KB (an 82% cut, 27 KB on the QA company by the audit). Equal outputs were checked by an md5 over the ordered answer, old against new, for every project on both bases, with a period, and with the flag (the same keys less the unused ones). The audit's own measure of `project_investment` on the 14 QA projects, with only the `line_in_cash` change, was 1,082 ms to 329 ms in total. The new `get_project_speed` pgTAP file pins both. No decision or screen changes.
