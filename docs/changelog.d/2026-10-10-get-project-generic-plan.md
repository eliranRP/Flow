`get_project` plans its large page query once per connection and reuses that plan. Before, Postgres planned it again on most calls, because plpgsql tries five custom plans before it reuses one and a pooled REST connection rarely gets that far. Planning was about half of a call's time. Repeat calls on a connection now take about 75 ms instead of 117 to 130 ms on local sandbox-size data. The first call on a new connection is unchanged. Results are the same: generic and custom plans gave identical output on 750 local cases. Neither plan scans the transactions, allocations or line splits tables in full. The project page speed test now also checks that the setting is still in place.
