# A change is saved on the tap, and again when the sheet is left

**Date:** 2026-09-29
**Status:** Accepted

## Context

On production (`da3a9c1`) a split expense kept its old category after Change assignment. The expense was 3,200 ₪ on 01/07/2026, split across six projects. The category picker showed the new row checked. After leaving the sheet, the transaction still had the old category, on the server and after a reload.

The round 8 function did not regress. `set_transaction_category` still updates only `category_id` and `user_assigned`. Shares, `pnl_role`, and `project_id` stay. Round 17 repeats that for six shares. The check was local React state. The write ran only from שמירה / שמירה ואישור. Closing the sheet copied the server row back over the check, so the tap was thrown away.

## Decision

1. A tap on a project or a category in the change sheet writes immediately. That is `reassign_transaction` for an ordinary row, and `set_transaction_category` for a split (`pnl_role` shared, an `unallocated_shared` review, or more than one share). The chosen row is busy: `aria-busy`, cursor progress. The other rows are not-allowed until that write finishes. Then the summary shows the name. A failure rolls the check back to the previous id, stays on the picker, and toasts. The picker is a tall sheet, and focusing a row can scroll the header out of that sheet. A toast that followed the scrolled header sat above the screen, so ניסיון חוזר could not be tapped. The toast now stays inside the viewport: in the visible gap above the sheet, or just under the sheet header when that gap is too small. This amends the off-screen placement in [0074](0074-toast-and-remembered-supplier.md). A dropped connection or a server error offers ניסיון חוזר, and that retry writes the choice that failed, not the rolled-back one. Any other refusal has no retry. A project tap on an unallocated shared cost toasts "עלות משותפת מחולקת במסך החלוקה." with לחלוקה, rolls the check back, and does not call `resolve_review`. This amends [0065](0065-review-round5.md) point 38, which returned to the summary and waited for a save button, and [0068](0068-review-round9.md) point 2, which put שמירה / שמירה ואישור on that summary.
2. Leaving the sheet saves whatever is still pending. That includes the backdrop, the X, a swipe down, the back chevron, and browser back. Pending means the owner changed something that has not been written yet. An unchanged sheet is not pending: ✕, the scrim, back, and a swipe close it and do not call `resolve_review` or `reassign_transaction`. The incomplete check still runs on every close, and it does not write. An incomplete assignment (a missing project or category) does not write and does not close. The summary shows "בחרו קטגוריה." or "בחרו פרויקט וקטגוריה." Split works the same way: a valid dirty choice calls `save_split` on the way out, and an invalid one stays open. The summary already says why ("נשארו N% לחלק", "הסך X%. צריך 100%.", or "בחרו לפחות 2 פרויקטים"). An unchanged split closes without a write. Amended by [0081](0081-review-queue-list.md) §4: ✕ on a picker that was not opened from a card line returns to the summary and leaves the sheet open.
3. The summary save button is removed, on the change sheet and on Split. The tap and the leave are the save. The new-project name still has שמירה. The name is typed, and that button is what creates the project. Once the project exists, assigning it is the same write as a tap.
4. A remember change that cannot be written again does not close silently. `resolve_review` is the only write that stores "לזכור לספק הזה", and it runs once, with the assignment. After that, flipping the switch and leaving keeps the sheet open and shows "הזכירה נשמרת עם השיוך. החזירו את המתג כדי לסגור." Turning the switch back lets the sheet close. A split never calls `resolve_review`, so the sheet does not show the toggle or its "← פרויקט · קטגוריה" preview. There is nothing to store.
5. The saving row shows a small spinner in place of the check, plus the progress cursor. The spinner in that radio is `--spinner-radio` (12px), one token shared by the app and Storybook. The other options in that picker or on the split screen are really disabled until the save settles: `disabled` or `aria-disabled`, the disabled text colour, and the not-allowed cursor. The cursor alone is not the disabled state. Busy still wins with the progress cursor on the row that is saving.
6. A dismiss during an in-flight save waits for the save to finish, then closes. The dismiss is never dropped. A save that succeeds is not discarded.
7. A toast that does not fit in the gap above an open sheet keeps its full height `--space-2` below the safe area. It is never clipped, and it never shrinks below two lines. It may cover the grabber and the empty top of the sheet. It never covers a header control (✕, back, title actions) or any other control, in any frame. The gap is `--space-2` at every size and safe area, including between the toast and the screen edge, so a one-line toast does not sit at y=1.5. The toast's height is measured once, before it is visible. The pad is computed from that height and the sheet's resting layout, never from a rect taken while the sheet is still opening. The open animation can leave the panel scrolled, which reports ✕ above the sheet; the resting control is the visible top plus that scroll, minus the drawer's translate. A tall sheet's pad pushes ✕ down, so the need is the unpadded control. A fit sheet is bottom-anchored, so a pad lifts its top and does not move ✕; the toast is placed against the top the sheet will have once that pad is gone. At safe area 0, ✕ is already clear and the sheet keeps its own `--space-2` padding. A 320 two-line refusal pads to 20 at safe area 20 and to 47 at safe area 47, and ✕ sits at the toast's bottom plus `--space-2`. The pad is one 200ms move with `--dur-base` and `--ease-standard`. The toast fades in only after that move finishes, and no frame shows it at opacity above 0 except at the position it settles at. A new toast waits until the sheet's shape (tall or fit) is the same across three frames, so a pick that returns to the short summary does not flash the tall position. If no pad is needed, it appears at that settled position. The height is not measured again during that toast, except when the sheet's own layout changes, for example from the tall picker to the short summary. Then the toast and the pad are placed again before the next paint, and the gap above the short sheet is `--space-2`. Under reduced motion that pad is removed in the same frame, with no one-frame leftover. When the toast leaves, the pad returns in one 200ms move. When no control is under the toast, the sheet pads nothing. The pad phase owns the layout: a resize caused by the pad itself does not cancel the move or the fade, and the sheet is snapshotted after the saving row has settled. A following toast is measured on the unpadded sheet and keeps the pad it already has, so the pad does not fall to 0 between them. A visible toast is placed again when the window resizes, the screen rotates, or the keyboard opens. That placement does not run during the pad or the fade. The timer does not run while the toast is hidden. This amends the "just under the sheet header" placement in point 1, and the r29 rule that clamped the toast into that gap.
8. An incomplete change still stays open the first time it is dismissed, and the summary says why, in the muted hint (`.t-hint`, text-muted) on both the change sheet and the split screen. ביטול השינוי sits next to that sentence. It uses the quiet secondary link, not the violet accent link. It discards the change and closes through the sheet's own close, not through the first dialog on the page. A second dismiss does the same. The discard flag resets when the sheet opens and when it closes. This amends the rejected alternative below: the first leave still does not throw the change away.
9. After a review item closes, a second pick on an income row calls `reassign_transaction` with a null project. Income is not assigned to a project. An empty project id is not a missing project for that write.
10. The reviewer queue uses the same `list_review` split fields as the app: `pnl_role` and `share_count`. The sample includes a split that is missing a category and an unallocated shared cost. A split never asks for a project. A category tap saves, the sheet stays open until ✕, and the card shows the new category. The same path is the live change sheet, not only the reviewer.
11. A category the owner picked is not labelled הצעה, in the app and in `/reviewer`. `list_review` returns `category_suggested`. After that category is saved on a split, אישור is enabled. The stories show the same states.
12. אישור on a categorised split calls `approve_split_review`. It closes the review item and leaves every share, amount, role, and the supplier rule untouched. It does not call `resolve_review`. An unallocated shared cost with no split yet still opens Split, and that function refuses it. Income and a row that is not a split are refused too. A sumit row created today then appears on שויכו היום, because the review is no longer open, and the transaction still carries its shares. (Amended 2026-10-08, FLOW-309: the banner reads "filed automatically", so a line the owner approved, changed or skipped in review no longer appears there; Eliran chose automatic only.) ביטול calls `reopen_review`, which puts the snapshotted shares back and takes the row off that list. The reviewer preview does the same for ברגי העמק: the approved split is added with both shares, and ביטול removes it. Approve and undo refresh `filed-today` and the transaction.
13. הצעה belongs to a line, not to the whole card. It shows only when that line is a real suggestion. A split line, including "מפוצל · N פרויקטים" and "עלות משותפת · טרם פוצלה", is never a suggestion. A guessed project on a rule-owned category shows הצעה on the project line only. `list_review` returns `project_suggested`. A project line shows הצעה only when that is true: a project the owner assigned, or one the supplier rule remembers, does not. The change sheet sets its suggestion id from `project_suggested === true`, not from the project id alone. A split card that only needs a category has no הצעה heading. An owner pick clears the category line's הצעה, including a pick of the suggested category itself. The picker tag is the same SuggestTag. The ReviewCard stories use the same marks as the queue.

## Alternatives rejected

Keeping שמירה ואישור as a second confirm after the tap. The tap is the confirm. A second button is what dropped the category on the phone.

Closing an invalid split on the first dismiss and discarding the percents. The owner asked that a change happen when they leave, and that an invalid one not disappear the first time. A later ruling (point 8) adds ביטול השינוי and a second dismiss, which do discard.

Calling `resolve_review` a second time to store a later remember toggle. The review item is already closed, and the call fails.

## Consequences

The transaction sheet stays open after a successful tap, with "השיוך נשמר" and ביטול when the write returned an undo id. Closing it does not undo the write. A review tap that resolves the item also stays on the sheet until the owner leaves; leaving returns to the queue.

`list_review` reports `pnl_role` and `share_count`. A category tap on any split in the queue calls `set_transaction_category` and keeps the shares. A project tap calls `collapse_split`, with the note and ביטול. The sheet does not ask for a project on a split. After the review item closes, the loaded row stays so a second pick can call `reassign_transaction`. There is still no separate write for a remember toggle after the assignment. That remains an open question.
