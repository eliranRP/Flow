# Settings → התראות: this device has its own row, the switches are for the whole account, and a test push

**Date:** 2026-10-20
**Status:** Accepted
**Amends:** [0193](0193-client-privileges.md) (`push_unsubscribe` is granted back to `authenticated`), [0095](0095-mcp-first.md) (no MCP tool for a device-bound action)

## Context

FLOW-502 put three switches on `/settings/notifications` (תנועה חדשה, תזכורת ערב, סיכום שבועי). They are stored per user, while a push subscription is per device. Turning a switch on from a device with no subscription asked the browser for permission and subscribed it; turning one off only saved. The owner reported that on an iPhone (Home Screen app) turning notifications on never showed the iOS prompt. What was found:

- The account's switches were already on, from another install. The Home Screen app in use had never been asked for permission (Flow did not appear in iOS Settings › Notifications). The only Apple subscription on the server belonged to an earlier install, so every evening's push was "sent" to a device that no longer showed it.
- A switch that is on can only be turned off, so `subscribeThisDevice` was never called from that iPhone. The screen never said whether this device was subscribed, and the same switches read the same on the computer and on the phone.
- When the owner turned a switch off and on, iOS asked and the owner allowed it, but the screen stayed busy: no `push_subscribe` call reached the server. After a reopen the toast said "לא הצלחנו להפעיל תזכורות." and still nothing was saved. Only the worker's `ready` had a timeout; `getSubscription`, `unsubscribe`, `subscribe` and the save could each wait forever, and every failure read the same.
- The app dropped the browser's subscription on any session end, an expired one included. The permission stays granted, so iOS never asks again, and the device silently stopped receiving.
- There was no way to check that pushes arrive, and a failed send was logged only as a count.

## Decision

- **This device has its own row**, "המכשיר הזה מקבל התראות", at the top of the page, with its own switch. On asks for permission and subscribes this device, called straight from the tap with nothing awaited before it. Off unsubscribes this device only: the browser's subscription and its server row (`push_unsubscribe`). No other device changes. The row's hint says the state: "התראות פעילות במכשיר הזה", "ההתראות לא מגיעות למכשיר הזה", or, when the permission is blocked, where to allow it: on an iPhone or iPad "בהגדרות של האייפון › עדכונים › Flow" (the iOS Settings app, Notifications, Flow), elsewhere the browser's settings. An iPhone tab and a browser that cannot push keep the existing notes, and the row cannot turn on. The state is read from the browser (`Notification.permission` and the worker's push subscription made with this build's key), each call with a timeout, and honours `pushSupport()`.
- **The three switches are what to receive, for every device of the account** ("מה לקבל · לכל המכשירים"). They save the preference only; they never subscribe or drop a device, and they can be changed from any device.
- **Connected devices.** "מכשירים מחוברים" lists the caller's own subscriptions, newest first: a short name read from the stored user agent (iPhone, iPad, Android, "Chrome במחשב" and so on), when it was added ("נוסף 09/10"), and "המכשיר הזה" on this device's row. The read is `list_my_push_devices()`: stable, `security definer`, the caller's rows only, with no endpoint and no key; this device is matched by a tag, the first 16 hex digits of the endpoint's SHA-256. When a switch is on and no device is connected, a line asks to connect this device. Removing another device from the list is left for later.
- **A test push.** "שליחת התראת בדיקה" sits under the device row while any device is connected, and sends one push ("התראת בדיקה · כך ייראו ההתראות מ־Flow", opening this page) to every connected device of the caller. It is push-send's kind `test`: the only path into push-send that takes the user's own JWT, and it refuses the cron secret and the service key. push-send calls `claim_push_test()` with the caller's JWT and the anon key, so PostgREST checks the token and the database names the user (`auth.uid()`); push-send never decodes the token itself and takes no user id from the request. The claim allows 5 test pushes an hour per user (a per-user advisory lock serialises two quick taps), spends nothing for a user with no device, and is recorded in `private.push_test_sends` (RLS, no policy, rows older than a day dropped on the next claim). push-send then reads that user's devices with the service key (`push_test_targets(p_user)`, `service_role` only, so endpoints and keys never reach a browser) and sends. The answer is `{devices, sent, gone, failed}`, or 401, or 429 `push_test_limit`; the app shows a toast for each.
- **A turn-on always settles and says why.** After the permission prompt every step has its own timeout and reason: the worker getting ready (10 s, `worker-timeout`), the page being controlled by the worker (3 s, then on), the existing subscription (10 s, `lookup-timeout`, or `lookup-threw`), subscribing (20 s, `subscribe-timeout`, or `subscribe-threw`), dropping an old one (10 s, `unsubscribe-timeout`) and the save (10 s, `save-timeout`, or `save-failed`). The prompt itself has 2 minutes (`permission-timeout`) and reads `denied` or `dismissed`; a subscribe that fails on a page the worker does not control yet reads `not-controlled` ("צריך לסגור את Flow ולפתוח שוב"). An outer limit backs them all, so the busy state always clears. A subscription made with another key is not unsubscribed first: the app subscribes fresh, and only when the browser refuses with `InvalidStateError` or `AbortError` does it drop the old one, wait 500 ms and try once more. Each reason has its own Hebrew line, and under the device row a muted line keeps the last step, the reason and the browser's error name and message ("שלב אחרון: הרשמה במכשיר (subscribe-threw · AbortError: …)"), with no endpoint or key, so a screenshot names the failing step. The review card and setup step 7 use the same reasons; step 7 stays on the page with the reason and finishes on the next tap.
- **An expired session keeps the subscription.** Only an explicit sign-out (Settings › יציאה) drops it, and that also deletes its server row through `push_unsubscribe` while the session still works; every step has a timeout and never blocks the sign-out. A different user signing in on the same browser drops it locally: the app remembers which user saved the subscription (`flow-push-user` in local storage), so this holds after a reload or an expired session too. The server deletes that endpoint on its next send (410).
- **The review card** is hidden when the evening reminder is on and this device (not any device) is subscribed.
- **Failed sends are logged** with the push service's host, the HTTP status (or the error's name) and the first 120 characters of the answer, with URLs taken out: never the endpoint's path, a key or a token. An RPC failure in push-send logs its name and status.
- **No MCP tool.** Subscribing, unsubscribing and the test push act on the browser the person holds; an agent has no device to subscribe. The switches' preferences are not MCP tools today either. This amends [0095](0095-mcp-first.md) for device-bound actions, which have nothing an agent could do.
- **0193 amended.** `push_unsubscribe(text)` is executable by `authenticated` again and is on the `privilege_guards` allowlist; the list of revoked unused RPCs is now 10. `claim_push_test()` and `list_my_push_devices()` join the allowlist; `list_my_push_devices` is in the smoke's `readRpcs`.

## Alternatives rejected

**Keep the switches per device.** Moving the preferences to the subscription row would mean three switches to set on every device and a migration of the stored preferences; the owner chose shared switches and a device row.

**Re-subscribe automatically on every open.** A permission request must come from a tap, and a silent re-save of a stale subscription would hide exactly the state the owner could not see.

**A separate edge function for the test push.** push-send already holds the VAPID keys, the encryption and the send budget; a small user path there with its own claim keeps one sender.

**Rate-limit in the edge function.** The function keeps no state between calls; the database claim is atomic per user and survives cold starts.

## Consequences

One migration (`20261020192620_push_devices_and_test.sql`) and a pgTAP file (`push_test.test.sql`). push-send needs `SUPABASE_ANON_KEY`, which the platform sets for every function. A device that was subscribed before this change has no remembered owner, so a different user signing in keeps it until it is turned off or the server drops it. The owner's iPhone needs one tap on the device row, from the Home Screen app, to subscribe.
